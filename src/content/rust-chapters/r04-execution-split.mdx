## 1. 工程痛点：普通写法为什么会在实盘翻车？

当基金要买入 100,000 股某股票时，执行算法（TWAP / VWAP）会把这笔**父单（Parent Order）**拆成几十笔**子单（Child Order）**分时段发出。实盘里最惊险的“超买事故”往往不是算法逻辑写错，而是下面两个细节没守住：

1. **整数除法把余数丢了，或者向上取整把总量买超了**：把 100 股按 3 个时间片均分，如果每片发 `100 / 3 = 33` 股，最后少买 1 股；如果每片向上取整发 34 股，最后多买 2 股。
2. **撤单还没确认就急着重发（最致命的并发超买）**：子单 A 挂了 1,000 股没成交，执行器发出了撤单指令，子单进入 `PendingCancel` 状态。如果执行器以为“反正已经撤了，额度释放了”，立刻又发出一笔 1,000 股的子单 B，结果交易所发来回报：“子单 A 撤单失败，就在 1 毫秒前已经全部成交！”——两笔同时成交，父单瞬间超买 1,000 股。

解决之道只有一条铁律：**容量守恒不变量**——在撤单被交易所最终确认（`Canceled`）之前，`PendingCancel` 的剩余数量依然必须 100% 占用父单额度。

  code={`#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ChildStatus {
    Working,
    PendingCancel,
    Filled,
    Canceled,
}

pub struct ChildSlice {
    pub orig_qty: u64,
    pub filled_qty: u64,
    pub status: ChildStatus,
}

pub struct ParentOrder {
    pub target_qty: u64,
    pub children: Vec<ChildSlice>,
}

impl ParentOrder {
    pub fn available_to_release(&self) -> u64 {
        let committed: u64 = self.children.iter().map(|c| match c.status {
            ChildStatus::Working | ChildStatus::PendingCancel => c.orig_qty,
            ChildStatus::Filled | ChildStatus::Canceled => c.filled_qty,
        }).sum();
        self.target_qty.saturating_sub(committed)
    }
}`}

## 4. 工程检查清单

- **拆单总量必须精确守恒**：所有子单切片之和必须严格等于 `target_qty`，用整数余数分配取代浮点乘法与四舍五入。
- **`PendingCancel` 视同活跃在途占用**：在收到交易所明确撤单终态前，绝不提前释放任何剩余额度。
- **每次发子单前重算 `available_to_release()`**：不要靠手动加减一个容易漏改的 `remaining` 缓存变量，直接从子单状态聚合最稳妥。
