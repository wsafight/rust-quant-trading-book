## 1. 工程痛点：普通写法为什么会在实盘翻车？

很多团队把风控写成策略里的几行 `if pos > max_pos { return; }`，这种“软风控”在极端行情下形同虚设，主要有三大致命漏洞：

1. **只看当前持仓，漏算在途买单与未知单（`Uncertain`）**：当前净持仓是 `0`，限额是 `100` 手。策略在 10 毫秒内连发 5 笔 80 手的买单，由于还没成交，每次查 `current_pos` 都是 `0`，于是 5 笔全部放行——1 秒后全部成交，净多头瞬间飙到 `400` 手直接爆仓。
2. **行情已经断流卡死，风控却照常放单**：行情网关卡住了 5 秒，策略拿着过期的假价差疯狂扫单，风控如果只看金额不查行情新鲜度，就会眼睁睁看着账户在盲飞中失血。
3. **风控和策略耦合，异常时默认放行（Fail-Open）**：为了“不影响交易机会”，有人在遇到行情缺失或算术异常时选择跳过检查放行。实盘里，**宁可漏赚十次，绝不多爆一次**，硬风控必须独立于策略，且严格执行 **Fail-Closed（任何异常默认拒单）**。

## 2. 核心 Rust 设计与在线语法点读

下面这段前置硬风控闸门完全是**无副作用纯函数**：它只接收一份栈上可 `Copy` 的只读快照 `RiskSnapshot`，依次校验 Kill Switch、行情新鲜度、最坏多空敞口（`worst_long` / `worst_short`），并输出结构化的 `RiskDecision` 供审计。

#[derive(Debug, Clone, Copy, PartialEq, Eq)]

    StaleMarketData,
    ExposureOverflow,
    PositionLimitExceeded,

pub fn pre_trade_check(
    snap: RiskSnapshot,
    limits: RiskLimits,
    order_signed_qty: i64,

    if snap.kill_switch_armed {
        return RiskDecision::Reject(RejectReason::KillSwitchActive);

        None => return RiskDecision::Reject(RejectReason::ExposureOverflow),

    if worst_long > limits.max_abs_position || worst_short < -limits.max_abs_position {
        return RiskDecision::Reject(RejectReason::PositionLimitExceeded);
    }
    RiskDecision::Allow

留意 `worst_long` 与 `worst_short` 的对称计算：
- **最坏多头敞口**假设所有在途买单（含 `Uncertain`）和本次新买单**全部成交**，而所有在途卖单**一手都没成交**；
- **最坏空头敞口**假设所有在途卖单（含 `Uncertain`）和本次新卖单**全部成交**，而所有在途买单**一手都没成交**。

只要把这两条最坏边界同时锁死在 `[-max_abs_position, +max_abs_position]` 之内，无论交易所按什么顺序成交，账户都不可能突破持仓红线。

## 4. 工程检查清单

- **硬风控独立成无副作用纯函数**：只吃只读 `RiskSnapshot`，绝不混写在策略业务代码里。
- **最坏敞口必须计入全部在途与 `Uncertain` 单**：买方与卖方最坏敞口分开独立计算，绝不拿未成交的对向挂单互相抵扣。
- **全维度 Fail-Closed**：Kill Switch 触发、行情过期、时间戳异常、算术溢出，任何一项异常均默认拒单并返回明确 `RejectReason`。
