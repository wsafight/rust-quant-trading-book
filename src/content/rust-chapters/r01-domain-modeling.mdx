## 1. 工程痛点：普通写法为什么会在实盘翻车？

在绝大多数原型脚本或弱类型系统里，下单函数往往长这样：`submit_order(price: f64, qty: f64)`。只要系统跑上几周，两个经典事故迟早会找上门：

1. **参数顺序传反，却毫无报错**：调用方一时手滑写成 `submit_order(qty, price)`，把“100 股”当成“100 元”，把“10.50 元”当成“10.5 股”。因为两者都是 `f64`，编译器和运行时都会放行，直到交易所瞬间扫穿盘口才发现酿成乌龙指。
2. **浮点精度漂移导致对账永久平不了**：在二进制 IEEE-754 浮点下，`0.1_f64 + 0.2_f64 == 0.30000000000000004`。挂单价差半个 tick 被交易所拒单，或者几万笔成交累积下来账本差了几分钱，财务对账系统直接告警锁死。

在量化核心引擎里，**金额、价格与数量绝对不能用 `f64`，也不能裸奔为 `i64`**。我们必须用整数最小变动刻度（Tick / Lot）表达所有数值，并借 Rust 的类型系统把“价格”和“数量”变成两种互不兼容的独立类型。

## 4. 工程检查清单

- **全链路禁用浮点记账**：价格、数量、手续费、盈亏统一使用整数刻度（`i64` / `i128`），只在展示层或研究统计层按需换算为小数。
- **所有领域 Newtype 保持字段私有**：通过 `new()` 返回 `Option` 或 `Result` 守住正数、非零等业务不变式，拒绝裸构造。
- **乘加运算一律升维并显式判溢出**：价格乘数量先转 `i128` 再走 `checked_mul`，把静默整数回绕扼杀在源头。
