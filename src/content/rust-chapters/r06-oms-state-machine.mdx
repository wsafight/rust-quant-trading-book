## 1. 工程痛点：普通写法为什么会在实盘翻车？

订单管理系统（OMS）面对的不是教科书里规规矩矩的线性流程，而是充满乱序、重传和超时的真实网络：

1. **成交回报比挂单确认（Ack）先到**：许多交易所的撮合通道和网关通道分离，你的订单刚发出还在 `PendingNew`，还没收到 `Ack`，就已经收到了一笔 `Fill`。如果状态机死板地拒绝“未确认订单的成交”，账本就会漏单！
2. **迟到的撤单拒绝把终态改回活跃态**：订单已经全部成交进入 `Filled` 终态，20 毫秒后才飘来一条早先发出的 `Ack` 或 `CancelReject`。如果直接覆盖状态字段，死单复活，策略或风控会对着已经结束的订单继续撤单或重复扣额度。
3. **下单超时后直接当成“失败”重发**：发出订单后 3 秒没回音，并不代表交易所没收到——可能只是回包丢了。此时贸然判为失败并重下第二单，一旦两笔都成交就是灾难性双倍持仓。正确做法是转入 **`Uncertain`（未知风险锁）**，在人工或对账查询确认前，风控必须按最坏情况计入敞口。

## 2. 核心 Rust 设计与在线语法点读

Rust 的带数据枚举（Algebraic Data Types）加上编译器强制的 `match` 穷尽检查，加上按值转移所有权（Move），天生就是写 OMS 状态机的神器。

pub enum OrderState {
    PendingNew { orig_qty: u64 },
    Live { orig_qty: u64, filled_qty: u64 },
    Uncertain { orig_qty: u64, filled_qty: u64 },
    Filled { orig_qty: u64 },
    Canceled { filled_qty: u64 },
}

pub enum OrderEvent {
    Ack,
    Fill { qty: u64 },
    Timeout,
    Canceled,
}

impl OrderState {
    pub fn apply(self, event: OrderEvent) -> Self {
        match (self, event) {
            // 终态单调不回退：忽略任何迟到事件
            (s @ OrderState::Filled { .. }, _) | (s @ OrderState::Canceled { .. }, _) => s,

            // 正常 Ack：待确认 -> 活跃
            (OrderState::PendingNew { orig_qty }, OrderEvent::Ack) => {
                OrderState::Live { orig_qty, filled_qty: 0 }
            }
            // 乱序吸收：成交比 Ack 先到，直接推进进度
            (OrderState::PendingNew { orig_qty }, OrderEvent::Fill { qty }) => {
                if qty >= orig_qty {
                    OrderState::Filled { orig_qty }
                } else {
                    OrderState::Live { orig_qty, filled_qty: qty }
                }
            }
            // 超时锁死为 Uncertain，绝不当成 Canceled
            (OrderState::PendingNew { orig_qty }, OrderEvent::Timeout) => {
                OrderState::Uncertain { orig_qty, filled_qty: 0 }
            }
            (OrderState::Live { orig_qty, filled_qty }, OrderEvent::Fill { qty })
            | (OrderState::Uncertain { orig_qty, filled_qty }, OrderEvent::Fill { qty }) => {
                let total = filled_qty.saturating_add(qty);
                if total >= orig_qty {
                    OrderState::Filled { orig_qty }
                } else {
                    OrderState::Live { orig_qty, filled_qty: total }
                }
            }
            (OrderState::Live { orig_qty, filled_qty }, OrderEvent::Timeout) => {
                OrderState::Uncertain { orig_qty, filled_qty }
            }
            (OrderState::Live { filled_qty, .. }, OrderEvent::Canceled)
            | (OrderState::Uncertain { filled_qty, .. }, OrderEvent::Canceled) => {
                OrderState::Canceled { filled_qty }
            }
            // 重复 Ack 或无影响事件：保持原状态
            (state, OrderEvent::Ack | OrderEvent::Timeout | OrderEvent::Canceled) => state,
        }
    }
}`}

## 4. 工程检查清单

- **超时绝不等价于撤单或失败**：任何未收到终态回执的超时单必须标为 `Uncertain`，禁止策略自动重试补单。
- **允许乱序推进，严禁终态回退**：`PendingNew` 可直接吸收 `Fill`；一旦进入 `Filled` 或 `Canceled`，对一切迟到事件免疫。
- **用所有权消费旧状态**：`apply(self, event) -> Self` 配合穷尽 `match`，把状态机遗漏留在编译期。
