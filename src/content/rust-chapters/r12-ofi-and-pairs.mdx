## 1. 工程痛点：普通写法为什么会在实盘翻车？

短周期微观结构策略（如订单流不平衡 OFI）与统计套利配对交易，在实盘里最常死于两类截然不同的工程缺陷：

1. **高频特征计算堆分配与分支遗漏**：OFI 每来一笔盘口更新就要计算一次买一/卖一队列变化。如果把历史快照塞进 `Vec` 反复分配、或者用层层嵌套的 `if / else if` 写价位对比，不仅微秒级延迟抖动严重，还极易漏掉“价位相等但挂单量变化”的分支；归一化时一旦盘口总量为 `0`，还会直接算出 `NaN`。
2. **配对套利“瘸腿裸奔”（Legging Risk）**：配对策略本质是同时做多 A、做空 B 吃价差回归。普通代码常用两个布尔值 `has_leg_a: bool` 和 `has_leg_b: bool` 拼状态。实盘中一旦 A 腿成交了、B 腿却因为行情跳空一直没成交，且没有显式的单腿超时强平与协整破裂止损，原本号称“市场中性”的套利策略就会瞬间沦为毫无保护的单边方向性赌博。

用 Rust 的 **`Copy` 栈结构体 + `Ordering` 三路匹配** 处理高频特征，再用 **带数据 `enum` 状态机** 锁死配对双腿生命周期，可以把这两类隐患一并消灭在编译期。

#[derive(Debug, Clone, Copy)]
pub struct TopOfBook {

pub fn compute_normalized_ofi(prev: TopOfBook, curr: TopOfBook) -> Option<f64> {
    let bid_flow = match curr.bid_px.cmp(&prev.bid_px) {
        Ordering::Greater => curr.bid_qty,
        Ordering::Equal => curr.bid_qty - prev.bid_qty,
        Ordering::Less => -prev.bid_qty,

        Ordering::Less => curr.ask_qty,
        Ordering::Equal => curr.ask_qty - prev.ask_qty,
        Ordering::Greater => -prev.ask_qty,
    };

    let depth = curr.bid_qty + curr.ask_qty;
    if depth <= 0 {
        return None;
    }
    Some((bid_flow - ask_flow) as f64 / depth as f64)
}`}

## 4. 工程检查清单

- **高频特征坚持栈上 `Copy` 零分配**：用 `Ordering` 三路匹配把盘口价位升/平/降全部写透，并在除法前加 `depth <= 0` 守卫。
- **配对套利严禁用零散布尔值管状态**：用 `PairState` 枚举显式区分 `Flat`、`SingleLegPending`、`Hedged` 与 `ForcedUnwind`。
- **单腿超时与协整破裂同等最高优先级**：只要单腿滞留超时或 `z_score` 失真/破限，立即切入强平动作，绝不幻想行情回头。
