# 第一部分导读：先让状态可以被相信

交易系统首先是状态系统，然后才是网络系统和策略系统。如果价格、数量、方向和订单状态可以被任意构造，后面加入异步、交易所接入与回测只会让错误更难复现。

这一部分不追求写出“像生产系统”的大框架，而是训练一种稳定的实现顺序：先定义事实，再限制状态，最后让错误和测试说明边界。

## 从一个判断逐步长成一个模块

八章形成一条连续路径：

| 章节 | 核心问题 | 留给下一章的产物 |
| --- | --- | --- |
| 第 1 章 | 如何建立可重复的开发闭环 | 可编译、可测试的最小 Rust 项目 |
| 第 2 章 | 如何表达纯计算和条件 | 中间价、价差、仓位判断等纯函数 |
| 第 3 章 | 谁拥有和修改状态 | 有明确负责人的持仓与快照 |
| 第 4 章 | 如何让非法状态难以出现 | 结构体、枚举、命令和事件模型 |
| 第 5 章 | 如何处理事件集合 | 与访问模式匹配的容器和迭代器 |
| 第 6 章 | 如何让失败显式且可验证 | 单位类型、错误分类与测试矩阵 |
| 第 7 章 | 如何建立可替换边界 | 小接口、测试时钟和适配器契约 |
| 第 8 章 | 如何把练习组织成工程 | 代码库、可执行程序、工作空间与自动检查 |

前几章的短例子会刻意保留一些简化。每当学到新工具，都要回看旧实现：裸整数是否应换成单位类型，多个真假值是否应换成枚举，函数是否拥有了不该拥有的数据，错误是否足以指导调用方行动。

## 带着这个场景阅读

假设你要实现一个函数：收到 best bid/ask 和当前仓位后，判断是否允许挂买单。

最初它只是五个整数和一个 `bool`。读完本部分后，它至少应该回答：

- 价格和仓位分别是什么单位，谁能构造它们？
- locked、crossed、溢出和缺失盘口怎样表示？
- 判断是策略建议还是不可绕过的风险决定？
- 配置由谁拥有，更新时是否会出现半新半旧状态？
- 测试如何覆盖 long、short、边界值与错误分类？
- library 的公开 API 是否允许调用者绕开不变量？

这还是离线逻辑，却已经具备后续实时系统所需的骨架。

## 本部分的阅读重点

不要把编译器错误当作学习障碍。所有权错误常常揭示的是“谁应该拥有状态”尚未决定，类型不匹配常常揭示的是单位或层次尚未说明。先用一句话解释错误保护了什么，再修改代码。

也不要过早追求抽象。只有当两个实现确实共享稳定行为时才引入 trait；只有当 crate 边界表达了团队或依赖边界时才拆 workspace。小而清楚的公开 API 比目录数量更能证明工程能力。

## 进入下一部分前

通过检查点一时，你应能从空目录建立一个 library + binary，使用私有字段保护领域值，用 `Result` 返回有行动含义的错误，并通过 fmt、clippy 和 test。更重要的是，你能解释哪些非法状态已经无法构造，哪些仍然只能在运行时检测。

第二部分会把这些可靠的纯逻辑放进持续运行的事件管线。届时，所有权会变成任务拓扑，错误分类会变成重连或停止动作，集合选择会直接影响延迟和背压。
