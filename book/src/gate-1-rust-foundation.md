# 阶段检查点一：类型安全的 Rust 工程

这个检查点验证第 1 至 8 章的知识是否已经变成可维护代码。通过之后再进入实时系统；如果所有业务值仍是裸 `i64`、错误靠 panic 处理，异步只会放大问题。

> **第一次使用建议**
>
> 检查点不是新知识，也不要求一次做出大型项目。先完成“统一验收场景”中的最小版本，再按自动验收逐项补测试。某一项做不出来时，直接使用文末的回补表返回对应章节，不必硬着头皮继续往后读。

## 为什么在这里暂停

语言概念单独练习时很容易显得都已掌握：所有权例子能编译，enum 可以写出来，测试也会使用 `assert_eq!`。真正困难的是让它们同时服务于一个公开 API。一个类型设计可能很安全却无法使用，一个错误枚举可能很完整却不能指导行动，一个 workspace 可能目录漂亮却允许任意模块绕开不变量。

本检查点刻意保持离线和单线程。这样一旦结果不正确，原因只来自领域建模、算术、API 或测试，而不是网络与调度。通过后再增加实时性，问题边界会清楚得多。

## 统一验收场景

使用一个最小“报价资格”场景贯穿所有任务：输入产品规则、订单簿顶部、当前持仓与候选买单，输出允许、缩量或拒绝，并给出结构化原因。

```text
decimal 配置/输入
  -> 严格转换为 ticks/lots
  -> 校验盘口与候选订单
  -> 计算成交后的最坏仓位
  -> RiskDecision
```

不要加入网络、数据库或完整策略。这个场景足以暴露单位混用、构造绕过、溢出、错误上下文和模块依赖问题。

## 前置条件

- 能解释所有权、借用、`Option`、`Result`、enum、trait 和 module 的用途。
- 已运行过仓库中的 `book/code` 配套工程，并能指出 `domain` 模块保护了哪些不变量。
- 开发环境可运行 `cargo fmt`、`cargo clippy` 和 `cargo test`。

## 必做任务

1. 建立一个 library crate 和一个离线 binary；binary 只能通过 library 的公开 API 修改状态。
2. 定义 `PriceTicks`、`QtyLots`、`ClientOrderId`、`Side` 和至少一个有上下文的错误类型。
3. 实现严格的 decimal-to-ticks、spread 和 position 更新；拒绝非法精度、非正数量及算术溢出。
4. 为订单命令或连接状态使用 enum，删除互相矛盾的 bool 组合。
5. 写一页依赖决策记录：为什么需要该依赖、feature、license、维护状态和替代方案。

## 推荐实施顺序

先从测试写出业务表，再实现类型：valid book、locked/crossed book、正常买入、到达 long limit、负数量、非法小数精度和算术极值。随后定义 `PriceTicks`、`QtyLots` 与 ID，使测试不能意外传错单位。

第二步实现不含 I/O 的纯函数，保持输入输出小而明确。第三步把它们放入 library，并让 binary 只负责构造输入和显示结果。最后再加入依赖记录、CI 命令和说明文档。这样每一步都有可运行状态，失败时也容易定位。

建议至少保留一次有意义的失败过程：例如先写会在极值溢出的实现，运行测试观察失败，再改为 checked arithmetic。只保存最终绿色输出，无法说明测试是否真的保护过边界。

## 自动验收

```bash
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-targets
```

测试至少覆盖：locked/crossed spread、`i64::MIN/MAX` 附近输入、非法 decimal 精度、long/short/反向持仓和错误类型匹配。不能用“测试里不会出现”回避边界。

## 人工演示

在 5 分钟内从空目录完成 `cargo new`、加入 library 模块、运行 binary 和一条失败后修复的测试。随后解释一个借用错误的根因，不能只说“编译器不允许”。

演示时让观察者任选一个变化：把 tick size 从 `0.01` 改为 `0.05`、把买单换成卖单、把 position 放到极值附近，或传入两个 venue 的同名 ID。你应能预测是编译失败、构造失败还是得到某个 risk decision，再运行验证。

## 评分量表

每项按 0–2 分，满分 10 分；任一“正确性与类型”或“错误与边界”得 0 分都不能通过。

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 正确性与类型 | 单位混用或非法状态可直接构造 | 核心类型存在，但边界仍泄漏 primitive | 公开 API 保持单位、身份和状态约束 |
| 错误与边界 | panic、哨兵或静默溢出 | 返回错误但上下文/行动含糊 | 错误有上下文并映射明确行动 |
| 所有权与 API | 依赖全局可变或大量无因 clone | owner 基本明确但接口过宽 | move/borrow 与状态 owner 能被解释 |
| 测试证据 | 只有 happy path | 有边界测试但缺极值或方向 | 正常、边界、非法与极值均覆盖 |
| 工程可重复 | 依赖个人环境或手工步骤 | 命令可运行但版本/说明不全 | 锁定版本、稳定命令和依赖记录齐全 |

建议达到 8 分以上再继续。分数不是能力标签，只用于决定回补位置；两次评审应保留具体 diff，而不是只记录总分。

## 通过证据

- 代码提交、完整测试输出和工具链版本。
- 一张 crate/module 依赖图，依赖方向无环。
- 一段 200 至 400 字说明：哪些非法状态已无法构造，哪些仍需运行时检查。

补充保存一份简短评审记录：输入 fixture、运行命令、失败过的边界、当前已知限制和下一步。不要提交 secret、真实账户数据或无法再分发的行情样本。

## 未通过时怎样回补

| 观察到的问题 | 回到章节 | 回补动作 |
| --- | --- | --- |
| 依靠 `clone` 或共享大锁才能编译 | 第 3 章 | 重画 owner 图，再缩小借用范围 |
| 多个 bool 可以形成矛盾状态 | 第 4 章 | 改成 enum 并列出转换表 |
| 价格、数量、ID 可互换 | 第 4、6 章 | 使用私有 newtype 和严格构造 |
| 错误只有字符串或 `unwrap` | 第 6 章 | 按调用方行动重新分类 |
| trait 很大、测试必须依赖真实 I/O | 第 7 章 | 从调用方需要的最小能力重新设计 |
| module/crate 相互引用或 binary 拥有业务逻辑 | 第 8 章 | 调整依赖方向和公开 API |

如果 API 允许任意整数直接成为价格或数量，回到第 4、6 章；如果通过大量 `clone` 或全局锁绕开所有权，回到第 3、7 章。

通过后冻结一次 tag 或 commit，并记录工具链版本。下一部分新增的订单簿、channel 与 Tokio 任务都应复用这里的领域类型和错误边界，而不是另建一套含义相近的 primitive 模型。
