# 第四部分导读：让不完整事实收敛为可信状态

交易所不会以本地函数调用的顺序返回事实。HTTP timeout 之后订单可能已经存在，成交可能早于 new ack 到达，撤单成功响应之后仍可能收到最后一笔成交，重连则会同时带来行情和私有状态缺口。

本部分构建交易系统最关键的闭环：忠实接收外部事实，通过状态机、幂等账本和独立风险边界，让系统在乱序、重复和部分失败下仍能收敛。

## 五章共同维护一条状态链

```text
原始行情 -> 已同步订单簿 -> 策略使用的状态快照
       |                                  |
       v                                  v
交易所适配器 <-> 请求/动作 <- 硬风控 <- 订单意图
       |
       v
私有事件 -> 订单状态更新 -> 成交事实 -> 账本/对账
```

| 章节 | 权威边界 | 主要失败模式 |
| --- | --- | --- |
| 第 18 章 | 原始行情与本地订单簿 | 消息缺口、数据陈旧、错误重同步 |
| 第 19 章 | 原始消息与领域语义转换 | 数据结构、精度、能力差异、限频 |
| 第 20 章 | 冻结协议契约 | 解码规则变化、产品说明不匹配 |
| 第 21 章 | 订单与成交状态 | 超时、乱序、重复、重启 |
| 第 22 章 | 决策和最大暴露 | 陈旧输入、未决订单、策略失控 |

不要让某个“方便的中心对象”跨越所有权边界。adapter 报告 venue 事实但不决定订单最终业务状态；OMS 收敛订单状态但不直接修改账本；策略提出 intent 但无权绕过硬风控；账本记录 execution 但不猜测订单是否仍活动。

## 带着最困难的五秒阅读

设想下面的事件同时发生：公开流缺一条 delta，策略刚发出一笔增险订单，写请求完成后 HTTP timeout，私有流断开，随后本地进程重启。

系统恢复时需要逐层回答：

- 旧 book 是否仍可用于定价？
- 本地 durable intent 和 send attempt 是否存在？
- 远端是否存在这张 client order ID 对应的订单？
- 断线期间是否产生 execution，能否去重入账？
- active、uncertain 和可能已成交数量怎样进入 worst-case exposure？
- 什么证据满足后才允许重新增险？

如果设计只能处理正常 ack 顺序，它还没有通过本部分。

## 固定样本怎样证明协议理解

接口文档描述规则，冻结的固定样本（fixture）保存某一版本下实际用于测试的输入。每个关键协议路径都应有原始消息、来源、访问日期、产品说明版本、预期标准事件和失败样本。

固定样本不能证明当前线上服务正常，也不能覆盖所有真实事件；它的价值是让数据结构理解、小数转换和消息编号规则可以在离线自动检查中重复验证。

## 进入下一部分前

通过检查点四时，你应能演示 fill-before-ack、cancel/fill race、重复 execution、请求 timeout、私有流断线和重启对账。任何未知状态都不能被自动解释成失败并重试；risk-off 期间仍要消费成交、撤单和对账事件，使风险逐步收敛。

第五部分会追问另一类可信度：离线结果能否代表当时真正可见、可成交的机会，以及系统进入生产后如何测量、降级和恢复。
