# 零基础预备课：先看懂一笔交易

如果你第一次接触量化交易，不必先记公式，也不必先知道交易所接口怎样工作。先跟着一笔订单走完全过程。后面章节出现的专业词，基本都能放回这条路径中理解。

## 1. 市场里有人想买，也有人想卖

假设某个产品当前有下面两条报价：

```text
有人愿意用 100 元买 2 个
有人愿意用 101 元卖 3 个
```

愿意买的一侧叫**买方报价**，常写作 `bid`；愿意卖的一侧叫**卖方报价**，常写作 `ask`。

现在最高买价是 100，最低卖价是 101。二者相差 1 元，这个差叫**价差**（spread）。两者的平均值 100.5 叫**中间价**（mid price）。中间价只是一个观察市场的参考，并不表示一定能在 100.5 成交。

许多买卖报价按价格排列在一起，就形成**订单簿**（order book）：

```text
卖方                            价格越低越容易先卖出
103 元：5 个
102 元：4 个
101 元：3 个  <- 最低卖价 best ask
-------------------------------
100 元：2 个  <- 最高买价 best bid
 99 元：6 个
 98 元：8 个
买方                            价格越高越容易先买到
```

订单簿不是“真实价值表”，它只是此刻公开显示的买卖意愿。报价随时可能增加、减少或撤销。

## 2. 立即成交，还是排队等待

如果你现在一定要买 1 个，可以接受 101 元的卖价。你的订单会立即与对方成交。你主动拿走了现有报价，因此通常称为 **taker**。

如果你只愿意用 100 元买，就可以挂一张 100 元的**限价单**。这张订单暂时不会成交，因为当前最低卖价是 101。它会与其他 100 元买单一起等待。你向市场提供了一个可见报价，若以后成交，通常称为 **maker**。

两种方式没有绝对好坏：

| 方式 | 好处 | 代价 |
| --- | --- | --- |
| 立即买入 | 更确定地完成交易 | 通常支付价差和更高费用 |
| 挂单等待 | 价格可能更好，费用可能更低 | 可能一直不成交，也可能只在行情变坏时成交 |

后面讨论“执行”时，核心就是在速度、价格、成交概率和风险之间做选择。

## 3. 发出订单不等于已经成交

程序希望买入时，先产生一个**订单意图**（intent）：

```text
我想以不高于 100 元的价格买 1 个
```

风险检查通过后，程序把请求发给交易所。之后可能收到几类不同消息：

- `ack`：交易所确认收到或接受了订单。
- `reject`：交易所明确拒绝订单。
- `fill` 或 `execution`：订单全部或部分成交。
- `cancel ack`：撤单已经生效。

这些消息不是同一回事。收到 `ack` 只表示订单被接受，不表示已经成交；收到 `fill` 才表示账户发生了真实交易。

消息也不一定按理想顺序到达。例如成交消息可能先到，接受确认后到。这叫 `fill-before-ack`。程序不能因为还没看到 `ack` 就丢掉这笔成交。

## 4. 超时只表示“我现在不知道”

假设程序发出买单，但两秒内没有收到响应。最危险的做法是直接认定失败，再发一张新订单。

第一张订单可能已经到达交易所，只是响应在网络中丢失。此时重新发送可能变成两张有效买单。正确理解是：

```text
本地事实：两秒内没有收到响应
远端事实：订单可能不存在，也可能正在等待，甚至已经成交
当前状态：未知，需要查询和对账
```

书中常用 `Uncertain` 表示这种未知订单状态。未知不等于错误，也不等于成功；在确认之前，它必须计入最坏风险。

## 5. 谁来记住订单走到哪一步

管理订单状态的组件常叫 **OMS**，即订单管理系统（Order Management System）。可以把它理解成一名严谨的记录员：

```text
准备发送 -> 等待确认 -> 活动中 -> 部分成交 -> 完全成交
                         |
                         v
                     请求撤销 -> 已撤销
```

OMS 接收交易所消息，根据明确规则更新状态。它还要处理重复消息、乱序消息、超时和进程重启。

书中常提到 **reducer**。它不是特殊交易术语，只是一类函数：给它“旧状态 + 新事件”，它计算“新状态 + 接下来要做的动作”。如果不在 reducer 中直接访问网络，同一批事件就可以反复重放并得到相同结果。

## 6. 成交后才改变仓位和账本

假设以 101 元买入 1 个，你的**仓位**（position）从 0 变成 `+1`。这里约定正数表示持有多头，负数表示持有空头。

之后价格涨到 103 元，这笔持仓暂时有 2 元未实现收益：

```text
(103 - 101) x 1 = 2
```

如果再以 103 元卖出，仓位回到 0，这 2 元成为已实现收益。真实结果还要减去交易费用，也可能包含资金费率、借贷成本和其他现金流。

保存这些经济事实的系统叫**账本**（ledger）。同一条成交消息即使收到两次，也只能入账一次，否则仓位和收益都会翻倍。

## 7. 为什么还需要对账

本地程序看到的消息可能不完整。断线期间，订单仍可能成交。因此程序会定期比较：

- 本地认为有哪些活动订单，交易所实际报告哪些订单。
- 本地累计了哪些成交，交易所历史成交中有哪些记录。
- 本地仓位和余额，交易所账户的仓位和余额。

这个过程叫**对账**（reconciliation）。发现差异后先保存证据、限制新增风险，再确定缺的是消息、规则还是本地实现。不能为了让数字一致而直接覆盖历史。

## 8. 程序怎样获得订单簿

交易所通常先提供一份完整订单簿，称为**快照**（snapshot）；之后不断发送“哪些价位发生变化”，称为**增量**（delta）。

每条更新通常带有递增编号。程序若收到 101、102、104，就知道 103 可能丢了。继续使用缺了一条更新的订单簿，结果虽然看起来合理，却可能完全错误。此时应停止把它交给策略，重新获取快照。

保存一小段原始消息作为固定测试输入，常称为 **fixture**。fixture 让断线、重复和缺失消息可以在不连接真实交易所的情况下反复测试。

## 9. 策略想做什么，风控允许做什么

**策略**根据市场数据和当前仓位提出订单意图。它可能判断 100 元值得买，也可能希望同时挂出买卖报价。

**硬风控**独立检查这项意图：行情是否仍新鲜，价格是否离市场太远，单笔数量是否过大，现有仓位和未决订单是否可能超过限额。最终结果通常是：

```text
允许 Allow
缩小数量 Resize
拒绝 Reject
```

策略不能自己提高硬限额，也不能绕过风险检查直接访问交易所。这样即使策略计算出错，最大暴露仍受到另一层约束。

## 10. 回测不是“用昨天的价格算今天能赚多少”

**回测**或**回放**是让程序重新经历历史事件。可信回测必须遵守当时的信息顺序：策略在某一时刻只能使用那时已经到达的数据，订单还要经过发送延迟、排队、部分成交和撤单。

一个**模拟交易所**会根据明确假设生成 `ack`、`fill` 和 `cancel` 消息。它不是未来预言器。成交假设越乐观，回测收益越可能虚高，因此书中会要求同时运行乐观、基准和悲观模型。

**校准**是把模拟结果与真实或影子运行观察比较，例如成交率、等待时间和成交后的价格变化。若差异太大，应拒绝模型或限制使用范围，而不是只把参数调到收益好看。

## 11. 全书常见词的白话对照

| 书中用词 | 可以先这样理解 |
| --- | --- |
| venue | 具体交易场所或交易所 |
| instrument | 具体可交易产品，例如某个现货或永续合约 |
| adapter | 把某家交易所的格式翻译成系统内部格式的适配器 |
| order book / book | 按价格排列的公开买卖报价 |
| snapshot / delta | 一份完整状态 / 完整状态之后的一次变化 |
| intent | 程序想做但还未成为远端事实的动作 |
| ack / fill | 接受确认 / 成交事实 |
| OMS | 维护订单生命周期的组件 |
| ledger | 根据成交和现金流计算仓位、现金与收益的账本 |
| reducer | 用旧状态和新事件计算新状态的纯逻辑 |
| fixture | 保存下来的固定测试样本 |
| replay | 按明确时间与顺序重新播放事件 |
| backpressure | 下游处理不过来时，系统怎样限制上游继续堆积 |
| tail latency | 最慢那一小部分请求或事件花了多久 |
| markout | 成交后一段时间价格向有利或不利方向移动多少 |
| risk-off | 停止增加风险，但仍继续处理成交、撤单和对账 |
| kill switch | 在明确范围内停止交易能力的紧急机制 |

现在不需要把这些词全部背下来。后续章节第一次深入使用时，会再次给出精确定义。你只需要先记住整条主线：

```text
先确认市场数据可信
-> 策略提出想法
-> 风控决定最多能做什么
-> 交易所返回部分事实
-> OMS 整理订单状态
-> 账本只按成交记账
-> 对账修复本地看不见的事实
```

读到某一节觉得抽象时，回到这条主线，先判断它正在解决哪一步的问题，再继续看代码。
