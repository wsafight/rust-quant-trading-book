# 第 18 章 行情、时钟与本地订单簿

行情系统的产物不是一个价格，而是一份带来源、序列、时间和可信状态的市场视图。数值看起来合理，不代表它仍然新鲜或来自完整事件链。

> **学习导航**
>
> - 开始前：通过检查点三，并理解订单簿、实时队列和网络连接。
> - 这一章学会：记录原始行情，判断本地订单簿是否连续、新鲜、可用。
> - 大约需要：14–20 小时。
> - 做完留下：行情样本、大规模回放、延迟报告和缺口演练。

> **开章场景：屏幕有价格，不代表行情可用**
>
> 本地屏幕仍显示 BTC 买价 60,000、卖价 60,001，程序也没有报错。但这两个数字是 8 秒前的，期间网络丢失了一条订单簿更新。若策略继续按它报价，真实市场可能早已移动；“有一个价格”与“这份价格现在可信”是两回事。
>
> 行情链路要保留收到的原始消息、交易所时间、本地接收时间和更新序号，还要能从完整快照接上后续变化。**本章要解决的是：怎样建立一份可以说明来源、连续性和新鲜度的本地订单簿，并在失效时停止使用。**

> **第一次阅读建议**
>
> 先读 18.1 至 18.9，抓住“收到消息、接上快照、发现缺口、停止使用、重新同步”这条主线。18.13 至 18.16 是存储、跨交易所时钟和异常排查的实现细节，第一次读不必记住其中所有指标与缩写。

## 18.1 行情接入层负责什么

行情接入层也常叫行情网关（market-data gateway）。它不是一个只负责“连上交易所”的程序，而是一条分工明确的处理流水线：

```text
网络连接 -> 原始消息解析 -> 按交易所规则同步 -> 转成内部统一格式
        -> 有容量上限的事件队列 -> 本地订单簿 -> 已验证的市场视图
```

- **网络连接层（transport）**管理 TCP、加密连接、WebSocket、心跳和重连。
- **解析器（decoder）**只把收到的原始字节或 JSON 消息，变成某家交易所定义的事件。
- **同步器（synchronizer）**按照这家交易所的快照、增量、序号和校验规则，判断消息能否连续接上。
- **格式转换器（normalizer）**把产品、价格和数量转换成系统内部统一类型，但不隐去原始含义和时间。
- **本地订单簿（local book）**只接收已经通过同步检查的事件。

这里的“统一格式”只是让上层代码使用同一组明确类型，不表示各交易所的规则变得相同。第 19 章会专门处理这些差异。

![行情数据流水线](assets/market-data-pipeline.svg)

*图 18-1：原始消息记录器与交易路径并行保存事实；任何同步规则失败，订单簿都进入不可用状态。*

不要把重连、解析、同步和策略计算全放进一个巨大的异步循环。分层之后，每一步都能用固定样本单独测试，也更容易定位故障发生在哪一层。

## 18.2 保存交易所发来的原始消息

转换后的统一数据便于研究，却不能替代交易所发来的原始消息。以后解析规则升级时，只有保留原始消息，才能用新代码重新处理，也才能确认交易所当时究竟发送了什么。

每条记录建议包含：

```text
venue, connection_id, channel, instrument
exchange_event_time, local_receive_time, local_record_time
venue_sequence/update_id, payload_length, raw_payload
schema_version, recorder_version, checksum
```

这些英文字段依次记录交易所、连接、频道、产品、各类时间、更新序号、消息长度、原始内容和版本信息。原始文件适合采用“只在末尾追加”的分段格式（append-only framing）：每条消息前写明长度，并保存校验值（checksum）。这样程序崩溃留下半条记录，或文件内容后来损坏时，都能被检测出来。长期存储可以压缩和分层，但格式版本不能被悄悄删除。

## 18.3 一条消息为什么需要多种时间

| 字段 | 中文含义 | 它回答的问题 |
| --- | --- | --- |
| `exchange_event_time` | 交易所事件时间 | 交易所声称事件何时发生？ |
| `local_receive_time` | 本机接收时间 | 我们何时真正看见完整消息？ |
| `local_process_time` | 本机处理时间 | 消息何时走到某个处理阶段？ |
| monotonic duration | 单调时钟计算的耗时 | 在不受系统校时影响的情况下，两步之间过了多久？ |
| `sequence` | 更新序号 | 消息的业务顺序是否连续？ |

研究必须使用当时已经到达本机的数据。不能事后按交易所时间重新排序，再假装程序当时已经知道那个顺序。比较不同交易所谁先变化时尤其要小心：时钟误差、网络线路和共同数据源，都可能制造出并不存在的领先关系。

## 18.4 连接状态不是布尔值

```text
Disconnected -> Connecting -> Subscribing -> Synchronizing
     ^                                            |
     |                                            v
Reconnecting <- Stale/Degraded <- Healthy <-------+
```

只有把完整快照（snapshot）与后续增量（delta）正确接上，并通过序号和订单簿规则检查，才能进入 `Healthy`（健康可用）状态。TCP 连接存在、心跳往返正常或收到订阅确认，都不能单独证明订单簿可以用于交易。

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum FeedState {
    Disconnected,
    Connecting,
    Subscribing,
    Synchronizing,
    Healthy { last_sequence: u64 },
    Stale,
    Reconnecting,
}

impl FeedState {
    fn can_publish_for_trading(self) -> bool {
        matches!(self, Self::Healthy { .. })
    }
}

fn main() {
    assert!(!FeedState::Synchronizing.can_publish_for_trading());
    assert!(FeedState::Healthy { last_sequence: 7 }.can_publish_for_trading());
}
```

## 18.5 完整快照怎样接上后续变化

完整快照是一份某个时点的完整订单簿；增量只描述此后哪些价位发生了变化。难点在于获取快照需要时间，这段时间里增量仍在不断到达，因此程序必须找到二者能够连续衔接的位置。

![Snapshot 与 delta 同步状态](assets/snapshot-delta-sync.svg)

*图 18-2：重新连网只恢复了连接；找到能接在快照序号 `S` 之后的增量并连续应用，订单簿才重新有效。*

各 venue 细节不同，但调查时可使用以下框架：

1. 建立增量消息流，并暂时缓存收到的变化。
2. 通过 HTTP 接口或 WebSocket 获取完整快照，记录它覆盖到哪个序号。
3. 丢弃已经包含在快照中的旧增量。
4. 找到协议定义的首个可衔接增量。
5. 连续应用后续增量，并验证校验值和订单簿规则。
6. 所有检查一起通过后，一次性发布 `Healthy` 订单簿。
7. 一旦发现序号缺口或校验失败，立刻标记为不可用并重新同步。

不同交易所的顺序并不完全相同：有些要求先拿快照再订阅，有些给出更新编号区间，有些要求核对上一条序号。上面的步骤用于理解问题，真实实现仍必须遵守目标交易所的官方规则。

## 18.6 用状态机说明订单簿是否可用

状态机就是“当前处于什么状态，收到某类事件后允许转到哪里”的明确规则。下面的代码表示：健康订单簿只接受下一条连续更新；若期望收到 11 却收到 12，就进入 `Invalid`（不可用）状态。

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum BookState {
    Empty,
    Synchronizing,
    Healthy { last_sequence: u64 },
    Invalid { expected: u64, received: u64 },
}

impl BookState {
    fn on_delta(self, sequence: u64) -> Self {
        match self {
            Self::Healthy { last_sequence } if sequence == last_sequence + 1 => {
                Self::Healthy { last_sequence: sequence }
            }
            Self::Healthy { last_sequence } if sequence <= last_sequence => self,
            Self::Healthy { last_sequence } => Self::Invalid {
                expected: last_sequence + 1,
                received: sequence,
            },
            other => other,
        }
    }

    fn is_tradable(self) -> bool {
        matches!(self, Self::Healthy { .. })
    }
}

fn main() {
    let state = BookState::Healthy { last_sequence: 10 }.on_delta(12);
    assert_eq!(state, BookState::Invalid { expected: 11, received: 12 });
    assert!(!state.is_tradable());
}
```

重复事件是否可忽略取决于协议，以及重复应用是否会改变结果。示例只表现“旧序列不回退”，真实实现还要用固定样本证明。

## 18.7 一条更新完整通过后再发布

处理一条增量更新时，安全顺序是：

1. 校验 instrument、sequence 和字段范围。
2. 把变化应用到只有一个任务负责修改的订单簿。
3. 检查最高买价、最低卖价、各档深度和校验值等规则。
4. 更新最后处理的序号。
5. 发布带版本的只读视图。

这五步应作为一个完整结果对外生效，不能让策略看到“价格已经变了，序号还没更新”的中间状态。如果某项失败，策略必须看见不可用状态，而不是继续使用上一次中间价。旧数据可以保留用于调查，但不能继续标成新鲜行情。

## 18.8 怎样判断行情是否过期

行情新鲜度（freshness）表示“这份市场状态离现在有多久”。年龄应使用本地接收或处理时间，与当前单调时钟比较。允许多旧取决于：

- 产品正常消息间隔和心跳规则。
- 策略关心多长时间后的价格，也就是预测周期（horizon）。
- 当前波动、买卖价差和仓位。
- 下单或撤单的网络往返时间（RTT），以及是否有其他价格来源。
- 当前能否可靠撤单与对冲。

因此可以分级处理：轻微变旧时扩大报价价差或缩小数量，超过硬阈值时禁止增加风险并撤销订单。最晚允许多旧必须有明确上限，不能完全交给策略临时决定。

## 18.9 重连与重同步不同

重连后要依次完成：

```text
网络重新连接 -> 重新订阅 -> 快照和增量正确衔接
-> 校验和业务规则通过 -> 行情足够新鲜 -> 策略才可交易
```

连续失败时，重试间隔应逐步拉长，并加入少量随机变化，这叫“指数退避加抖动”（exponential backoff with jitter）。它能避免许多任务同时重连，反复冲击交易所并触发封禁。新连接不能直接沿用旧订单簿，除非协议能够明确证明消息仍然连续。

## 18.10 行情背压

当消息解析速度高于订单簿处理速度时：

- 不能随意丢弃二档订单簿增量后继续发布，因为后续状态依赖前一条变化。
- 对彼此独立、旧值可以被新值完全替代的数据，可以只保留最新版本。
- 队列中最旧消息等待了多久，比单看队列长度更能反映策略是否在读旧市场。
- 长期过载时应把行情标为不可用并停止增险，不能用更大的无限队列掩盖问题。

计算队列容量时，需要知道峰值消息率、实际处理能力、高峰持续时间和最大可接受消息年龄。还应使用录制的极端行情，以 2 倍或更高速度回放来验证余量。

## 18.11 指标与告警

指标用于持续回答三个问题：连接是否存在，消息是否连续，策略拿到的行情是否仍然可用。下面保留常见英文指标名，方便对应代码和监控系统，但先按用途分组理解。

连接：

- 连接状态，以及最后一次收到字节、完整消息和有效事件的时间。
- 重连、重新订阅和重新同步的次数与耗时。
- 网络心跳与业务行情心跳。

数据：

- 每秒消息数、字节数和解析错误数。
- 序号缺口、重复、乱序和校验失败数。
- 从交易所事件到本机接收、从接收到处理完成的耗时，以及队列消息年龄。
- 订单簿是否有效、买卖价是否异常交叉，以及最优价格和多档深度。

告警必须结合系统动作。例如行情年龄已经超限，而策略仍允许交易，应立即通知值班人员；若系统已经自动停止增险，仍要告警，但严重程度可以根据剩余仓位和活动订单调整。

## 18.12 确定性回放

原始消息记录器（recorder）的输出，应能直接交给离线回放程序（replay）。同一批原始事件使用同一版本的解析与转换代码时，必须生成相同的统一事件、订单簿状态和最终校验值。纯粹计算订单簿的函数不应读取真实系统时间，也不应依赖随机重连或网络状态，否则同一输入可能得到不同结果。

回放测试至少注入：

- 删除一条增量消息。
- 重复一条增量消息。
- 交换两个事件。
- 制造校验值不一致。
- 让完整快照获取过慢，直到增量缓存装满。
- TCP 活着但长时间无有效事件。

## 18.13 如何保存原始行情

最简单、便于审计的原始消息记录器，可以使用只在末尾追加的分段文件：

```text
file header:
  magic | format_version | venue | connection_id | created_at

record:
  record_length | local_sequence | receive_time | payload_length
  | raw_payload | checksum
```

`record_length` 告诉读取程序一条记录有多长，校验值用于检测内容损坏和崩溃留下的半条记录。文件可以按时间或大小切成多个分片；清单文件（manifest）记录每个分片的首尾序号、时间范围、字节数、校验值、消息格式版本和记录器版本。

写入磁盘不能无限期卡住接收行情的任务。常见做法是：网络任务把自己拥有的一块消息内存放进有容量上限的通道，再由专门任务批量写入。通道快满或消息等待过久时必须告警，并根据审计要求决定是否停止增险。若系统声称原始行情是恢复证据，就不能在压力大时悄悄丢掉记录却继续交易。

账户订单和成交等私有消息，应与公开行情分开存储并分别授权。原始私有消息可能包含账户标识，不应进入普通研究存储区。日志只记录受控文件位置和校验值，不复制完整敏感内容。

## 18.14 如何安全完成重新同步

重新同步时，最好不要一边修复当前订单簿，一边继续把它标为健康。更安全的方式是在隔离的候选订单簿上工作：

```text
当前订单簿：不可用，保留旧版本用于调查
候选订单簿：载入快照 -> 应用缓存增量 -> 完整验证
如果成功：
  一次性把候选版本发布为新的当前订单簿
如果失败：
  丢弃候选版本，等待一段时间后重试
```

每次同步尝试都应带有唯一编号，并记录快照耗时、缓存消息数、失败原因和完成序号。这样即使短时间内反复重连，也能区分到底是网络连接失败、快照太慢、缓存装满、序号接不上，还是校验算法错误。

策略作出决定时，应同时记录订单簿版本、序号和接收时间。即使当前订单簿后来被新版本替换，历史决策日志仍能追到当时使用的完整状态。不要只记录一个中间价，因为事后需要知道决策究竟基于哪一份订单簿。

若多个产品共用一个 WebSocket，单个产品出现序号缺口后是否必须重连整个连接，要由协议规则决定。设计时应分别维护“连接整体是否健康”和“每个频道、每个订单簿是否健康”，既避免一个产品异常就无必要地停掉全部产品，也避免连接整体损坏时只修复局部。

## 18.15 比较不同交易所先后顺序的陷阱（进阶）

第一次阅读只需记住：不同交易所报出的时间不能直接互相比大小，因为它们使用不同机器时钟，消息到达本机还要经过不同网络路径。

假设 A 的 exchange timestamp 比 B 早 3 ms，不能直接得出 A 领先 B。可能的时间线：

```text
A 撮合时钟快 2 ms
A 消息网络耗时 8 ms
B 撮合时钟慢 1 ms
B 消息网络耗时 2 ms
本地先看到 B，事后 exchange timestamp 却把 A 排在前面
```

跨交易所研究至少要保留本机接收时间，并记录主机校时误差、网络路径和数据源位置。若能取得操作系统内核记录的收包时间，还应区分“数据包到达机器”和“应用程序读到数据”之间的延迟；否则程序自身暂时卡顿，可能被误判为网络变慢。

真正可执行的领先关系不是“哪家交易所写出的时间更早”，而是：某条信息到达本机后，等程序完成计算并把订单发到另一家交易所时，它是否仍能预测未来可成交价格。这个问题天然包含程序部署位置和发送延迟。

## 18.16 行情异常调试手册

看到买卖价格异常交叉或校验失败时，按证据层次调查：

1. 找到连接编号、频道、产品和本次同步尝试编号。
2. 从保存的原始消息重放，不只依赖进程内的临时日志。
3. 检查解析器是否保留了数字精度和“删除价位”的含义。
4. 对照官方同步规则检查快照与增量的衔接位置。
5. 判断重复和乱序来自网络，还是程序内部任务重新排列了消息。
6. 检查计算官方校验值前使用的排序、字符串格式和档位数量。
7. 确认产品规则或最小价格单位在事件期间是否变化。
8. 修复后用原始最小反例和完整窗口回归。

不要在原因未明时，简单删除“最高买价大于等于最低卖价”的档位来修正订单簿。这样会隐藏输入或同步错误，并制造出交易所从未存在过的本地市场。

## 18.17 本章交付

实现一个公开行情记录器和二档订单簿重建程序，连续运行并产出：

- 原始数据文件、格式说明和校验值。
- 正常情况与序号缺口的固定测试样本。
- 快照和增量同步状态图。
- 100 万个事件的确定性回放结果。
- 典型、中高和极端分位的“收到原始消息到更新订单簿”耗时，以及队列消息年龄。
- 一份重连、序号缺口和行情过期演练记录。

本章完成标准：系统任何时候都能回答“这份订单簿能否用于交易、最后连续序号是什么、最新消息多久以前收到，以及为什么相信它”。

## 18.18 回顾与下一章

行情接入层的责任不是不断输出结构化数据，而是保存原始事实、严格解析消息、维护连续性与新鲜度证据，并只在订单簿可用时发布计算结果。连接成功、序号连续、订单簿合法、数据新鲜和策略可以交易，是逐层递进的条件，不能压成一个“正常或异常”的布尔值。

原始消息记录和确定性回放，让线上观察可以在离线环境中复现。每条记录需要保留原始内容、接收时间、来源和格式版本；回放使用可控制的时钟，并复用相同的订单簿更新逻辑。发现买卖价异常交叉或序号缺口时，应保存证据并重新同步，不能靠删除“不好看”的档位制造本地市场。

下一章把范围从公开行情扩展到完整交易所协议。适配器将负责产品规则、小数转换、功能差异、身份编号、错误和请求频率限制，同时保留不同交易所之间无法安全统一的部分。
