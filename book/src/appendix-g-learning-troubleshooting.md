# 附录 G 学习故障排查

本附录处理的是“练习为什么推进不下去”，不是替代正文给出答案。遇到问题时，先缩小失败范围、保留原始证据，再改变一个条件验证假设。不要同时重写代码、替换输入、升级依赖和改变设计。

## G.1 通用排查循环

```text
记录原始现象
-> 判断失败层次
-> 缩小为最小反例
-> 提出一个可证伪假设
-> 只改变一个条件
-> 重复运行并比较
-> 保存反例和修复证据
```

先回答四个问题：

1. 预期行为具体是什么？
2. 实际行为具体是什么？
3. 使用了哪份输入、配置和版本？
4. 最近一次已知正确的状态是什么？

如果这四项无法回答，先补记录，不要继续猜。

## G.2 常见现象与优先动作

| 现象 | 优先动作 | 不要先做 |
| --- | --- | --- |
| 命令无法运行 | 检查当前目录、命令是否存在和第一条错误 | 反复复制同一命令 |
| 编译错误很多 | 只处理编译器报告的第一条根因 | 给所有值加 `clone` |
| 所有权错误反复出现 | 画出 owner、借用者和修改时点 | 立即使用 `Arc<Mutex<_>>` |
| 测试不稳定 | 固定输入、时钟、随机种子和事件顺序 | 增加重试掩盖失败 |
| 订单簿偶尔错误 | 保存最小消息窗口并检查 sequence | 用后续价格覆盖异常 |
| 异步任务卡住 | 列出每个任务等待什么、谁能唤醒它 | 增加无界 channel |
| PnL 对不上 | 按 execution 逐条核对 cash、position、fee | 增加“其他盈亏”填平 |
| 请求超时 | 标记业务状态未知并列对账证据 | 换新 ID 直接重发 |
| 回测很好但无法解释 | 检查时点、成交、成本、尝试范围 | 继续搜索更优参数 |
| 性能波动很大 | 固定构建模式、环境、负载和 checksum | 只报告最好一次 |
| 综合项目无法推进 | 回到最近未通过的 gate | 同时增加更多模块 |

## G.3 怎样阅读 Rust 编译错误

先忽略后续连锁错误，处理第一条具体诊断：

1. 找到文件和行；
2. 写下哪个值被移动、借用或需要某种类型；
3. 说明调用之后谁还需要这个值；
4. 判断正确动作是转移所有权、临时借用、缩小借用范围，还是改变状态 owner；
5. 修改后重新编译，观察剩余错误是否仍成立。

如果唯一解释是“编译器不让我这样写”，说明仍未理解保护的状态边界。

## G.4 怎样处理测试失败

测试失败至少有四种来源：

- 实现违反了已经确认的规则；
- 测试预期写错；
- 输入或环境不稳定；
- 规则本身还没有被定义。

先把失败缩小到最少输入。对于交易状态，保留事件顺序；对于数值问题，保留单位、方向和边界值；对于异步问题，替换 wall clock 和真实网络。修复后把最小反例加入固定回归，不要只恢复绿色结果。

## G.5 怎样处理“公式看懂但不会写”

用五步拆解：

1. 写出每个输入的含义、单位和允许范围；
2. 用三行以内的小数据手算；
3. 为 long/short 或 buy/sell 分别计算；
4. 写成不含 I/O 的纯函数；
5. 对照手算结果，并加入零值、负值和极值。

如果连手算方向都无法确定，先查产品定义，不要让代码替你猜。

## G.6 怎样处理“状态机越改越复杂”

不要从代码分支开始。先列：

- 当前状态；
- 输入事件；
- 允许的新状态；
- 是否产生外部动作；
- 重复事件怎样处理；
- 旧事件、乱序事件和未知事件怎样处理。

把表格中无法决定的格子标为“规则未知”，而不是用默认分支吞掉。随后选一条最短失败序列写测试，例如：`send -> fill -> ack` 或 `send -> timeout -> restart -> reconcile`。

## G.7 怎样处理“回测结果很好”

漂亮结果首先触发审查，而不是发布：

1. 决策时输入真的已经可见吗？
2. 模拟成交是否使用了同一时点之后的信息？
3. 费用、价差、延迟、排队和未成交是否进入模型？
4. 测了多少参数和信号，失败结果是否保留？
5. 最终数据是否真的没有参与选择？
6. 结果是否集中在一个短时段或单一市场环境？
7. 账务能否逐事件闭合？

先主动寻找能推翻结果的条件。经不起保守成交或小幅参数变化的结论，应降级为待研究假设。

## G.8 何时回到前一阶段

出现以下任一情况，应停止扩展功能：

- 公开 API 重新使用无单位 primitive；
- 同一状态有多个不清楚的写入者；
- sequence gap 后仍输出可交易价格；
- timeout 被解释成远端失败；
- execution 可以重复改变仓位或现金；
- 回放依赖 wall clock、文件顺序或未固定随机性；
- 研究报告无法追到输入版本；
- 恢复交易不需要对账和审批。

回到首次建立该契约的章节或 gate，修复后再继续。后面增加的功能不会自动弥补前置不变量。

## G.9 怎样有效求助

求助时提供：

```markdown
- 我想证明的行为：
- 最小输入：
- 运行命令：
- 完整的第一条错误：
- 预期与实际：
- 我已经验证的假设：
- 我尚不确定的规则：
```

不要只发送“运行不了”或一张截断截图。一个可复现的问题本身就是工程产物。
