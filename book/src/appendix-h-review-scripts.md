# 附录 H 阶段评审脚本

阶段检查点不应只由实现者自评。本附录让同伴即使没有通读全书，也能通过改变输入、注入故障和追问证据完成一次边界明确的评审。

评审不是寻找写法偏好，而是判断：输入是否明确，状态是否可信，失败是否有动作，结果能否复现，能力声明是否超过证据。

## H.1 通用评审流程

每次评审控制在 30～60 分钟：

1. 实现者用 5 分钟说明目标、范围和不能证明的内容。
2. 评审者仅按 README 或证据索引运行正常流程。
3. 评审者改变一个边界输入。
4. 评审者注入一个故障或打乱一个事件顺序。
5. 双方核对输出、状态、日志和最终证据。
6. 记录必须修复、建议改进和仍然未知三类结论。

通用追问：

- 这个事实来自哪里？
- 谁可以修改这个状态？
- 如果同一事件收到两次会怎样？
- 如果进程在这一步退出会怎样？
- 什么证据满足后才允许继续？
- 这项结果不能证明什么？

## H.2 Gate 0 评审：独立运行与定位

评审者操作：

- 从不同目录按照 README 运行；
- 删除或改名一个输入文件；
- 插入非法方向、负数量或重复行；
- 要求实现者展示修改前后的 diff。

通过条件：

- README 没有依赖口头步骤；
- 错误指出具体输入问题，不生成正常外观的结果；
- 实现者能从第一条证据定位，而不是随机修改；
- Git 提交不包含敏感或无关内容。

## H.3 检查点一评审：类型与 API

评审者操作：

- 尝试把价格传到数量位置；
- 尝试直接构造负数量或空订单编号；
- 输入 locked、crossed 和整数极值；
- 检查 binary 是否能绕过 library 不变量。

追问：哪些非法状态已无法构造？哪些仍需运行时检查？为什么这里借用而不是取得所有权？错误怎样指导调用方行动？

必须修复：单位可静默混用、错误靠 panic、溢出未处理、公开字段绕过构造规则。

## H.4 检查点二评审：实时管线

评审者操作：

- 删除一条 delta；
- 制造两倍或五倍短时 burst；
- 让业务消息停止但 heartbeat 继续；
- 在不同等待点触发 shutdown。

追问：每条队列为什么有这个容量？满载时谁阻塞或失效？进程健康、协议健康和交易就绪怎样区分？p99.9 是否包含排队时间？

必须修复：gap 后继续发布、无界关键队列、取消后遗留未知副作用却无记录、性能结论没有输入和 checksum。

## H.5 检查点三评审：产品、公式与账务

评审者操作：

- 把 long 改为 short；
- 改变 multiplier、fee currency 或 funding 方向；
- 重放同一 execution；
- 修改一笔 fee，观察 equity residual。

追问：每个值的单位和币种是什么？规则在哪个日期从哪个来源取得？分析归因能否修改账务事实？平均成本产生余数时怎样处理？

必须修复：方向只测一侧、同一成交重复记账、残差被“其他项”填平、历史事件使用当前产品规则。

## H.6 检查点四评审：交易闭环

评审者按以下序列任意暂停：

```text
intent persisted
-> send attempted
-> response timeout
-> private stream disconnects
-> fill arrives
-> process restarts
-> reconciliation
```

每次暂停都问：

- 远端可能有哪些活动订单？
- 已确认哪些 execution？
- 最坏 long/short 暴露是多少？
- 当前能否增险？
- 结论来自哪条事实？

必须修复：超时后换 ID 重发、未知订单不进入风险、策略绕过硬风控、重启后未对账便恢复。

## H.7 检查点五评审：研究与生产

评审者操作：

- 打乱输入文件顺序；
- 把延迟扩大十倍；
- 从 touch 改为悲观 queue 模型；
- 删除一条行情；
- 要求展示一项失败实验；
- 在恢复前制造一笔账务差异。

追问：输入何时对策略可见？最终 holdout 是否参与过选择？成交模型怎样校准？什么结果会 Reject 而不是继续调参？谁批准恢复交易？

必须修复：wall clock 进入核心决定、直接修改仓位、只保存胜出实验、PnL 不闭合仍继续、进程恢复即开放交易。

## H.8 最终项目评审

最终评审至少由一名未参与实现的人完成。实现者不能在第一次运行时提供口头提示，只能观察并记录文档缺口。

评审者需要：

1. 找到输入、配置和运行入口；
2. 完成正常演示；
3. 注入一个故障；
4. 复核一项账务、性能或研究结论；
5. 指出一项声明是否超过证据；
6. 根据项目方向连续追问十分钟。

最终记录模板：

```markdown
# 阶段评审记录

- 项目版本与输入：
- 评审范围：
- 正常演示结果：
- 注入的变化或故障：
- 观察到的状态与证据：
- 必须修复：
- 建议改进：
- 尚不能判断：
- 修复后的复验结果：
```

“评审者没有发现问题”不是充分结论。评审必须记录实际改变了什么、观察了什么，以及哪些范围没有覆盖。

## H.9 研究答辩记录

答辩者先用 5 分钟给出机制、数据、结果和决定，再接受至少 15 分钟追问。观察者不得只评价表达流畅程度。

```markdown
# 研究答辩记录

- experiment ID / report version：
- 机制与预先声明假设：
- decision information set：
- label interval：
- train / validation / holdout：
- 全部尝试数量和 family：
- effect size 与不确定区间：
- fee / latency / fill / capacity 敏感性：
- 展示的负结果：
- 阶段决定与停止条件：

## 观察者追问
- 哪个字段可能在决策时尚不可见？
- 哪组样本可能不独立？
- 哪个模型变化最容易推翻结论？
- 谁支付收益，为什么可能持续？
- 为什么当前决定不是更高阶段？

## 结论
- 已回答并有证据：
- 回答合理但缺证据：
- 无法回答：
- 必须补做的实验：
```

## H.10 事故演练观察员脚本

观察员在演练开始前只知道故障范围，不提前告诉执行者注入时点。记录事实与推断，不代替执行者操作。

```markdown
# 故障演练观察记录

- incident ID / system version：
- 注入故障：
- 注入时间：
- 首个可观察信号及时间：
- readiness 变化：
- 自动 risk-off 动作：
- 人工接管时间与负责人：
- 期间远端可能状态：
- 最坏暴露估计：
- order / execution / position / cash 对账：
- 恢复所依据的证据：
- 审批人与恢复范围：
- 未按预期发生的行为：
- 永久行动项、owner、期限和验证方法：
```

观察员至少检查：

- 告警是否早于资金后果；
- 自动动作是否真的减少或限制风险；
- risk-off 后是否继续处理 execution 与 reconciliation；
- 软件恢复是否错误地被当成外部状态恢复；
- PnL residual 是否阻止恢复；
- 处置手册是否包含必须口头说明的隐藏步骤。
