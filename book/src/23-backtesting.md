# 第 23 章 数据、回测与仿真

回测不是把历史价格喂给策略。交易系统在当时只能看到延迟、不完整且有协议顺序的数据；订单还要经历发送、接受、排队、部分成交、撤单和成交回报。忽略这些步骤，漂亮收益通常只是成交模型的产物。

> **学习导航**
>
> - 开始前：通过检查点四，已有可复用的订单簿、订单管理、风控和账本。
> - 这一章学会：按历史当时可见的信息，重新运行一套交易流程。
> - 大约需要：18–24 小时。
> - 做完留下：事件回放器、三类成交假设、成本敏感性和对账报告。

> **开章场景：回测总能买在最低点**
>
> 一根一分钟价格柱显示开盘 100、最低 95、收盘 102。策略用收盘时才能知道的完整价格柱作出买入决定，回测器却按这一分钟的最低价 95 成交。报告看起来像抓住了反弹，现实中却不可能先看到 102 的收盘结果，再回到同一分钟用 95 买入。
>
> 回测必须按当时可见的信息和真实先后顺序推进，订单还要经历延迟、排队、部分成交、费用和撤单。**本章要解决的是：怎样让历史数据重新经过同一套交易流程，而不是让程序暗中使用未来信息。**

> **第一次阅读建议**
>
> 先读 23.1 至 23.8，掌握三条底线：不能使用未来数据，不能看到价格触及就假设成交，不能让模拟器直接修改仓位。统计检验、模型校准和上线阶梯可在第一次完成简单回放后再读。

## 23.1 研究假设先行

开始写代码前，先用完整句子写清楚：

- 经济机制：谁支付收益，为什么会持续？
- 用什么输入产生交易信号，要预测什么结果，预测多长时间。
- 决策时点可见的数据。
- 使用什么订单、在哪家交易所执行，以及经过哪些步骤。
- 交易费用、资金费用、借贷成本、成交价偏差与市场冲击。
- 失效条件与容量边界。
- 哪段数据用于调整，哪段用于验证，以及哪段最终保留到最后才使用。

先写下假设，可以减少“先看到漂亮结果，再为它编一个解释”的自由度。

## 23.2 每个计算结果都要能追到原始数据

至少保留三层：

```text
交易所原始消息 -> 内部统一事件 -> 计算出的输入特征和未来结果
```

这种从计算结果一路追到来源的关系叫数据血缘（data lineage）。每份数据产物都应记录原始文件校验值、消息格式版本、适配和转换代码版本、配置、时间范围及输出清单。数据缺口本身也是重要事件，不能在断线期间悄悄沿用上一份订单簿来填空。

需要的数据通常包括：

- 二档订单簿快照与增量、市场成交、标记价格、指数价格和资金费率。
- 产品规则及其变化。
- 自己的订单意图、请求、确认、成交、撤单、仓位和余额。
- 费率等级、借贷、转账和结算记录。
- 本机接收与处理时间、连接状态和延迟。

## 23.3 当时只能使用当时已经看到的数据

时点一致（point-in-time）表示：策略在时刻 `t` 只能使用 `t` 之前已经到达本机的数据。常见的偷看未来错误包括：

- 事后按各交易所自报时间重新排列事件，忽略本机实际看到的顺序。
- 使用当天结束后才发布的产品规则，重新解释当天订单。
- 在一分钟尚未结束时，使用这根分钟价格柱的最终完整结果作决定。
- 用断线结束后的完整快照填补断线期间的未知状态。
- 先看到订单是否成交，再反推当时的排队位置。

回放时钟应由历史事件向前推进，核心策略不能直接读取电脑当前时间。下面的 `ReplayClock` 是一个由测试控制的时钟：

```rust
trait Clock {
    fn now_ns(&self) -> u64;
}

struct ReplayClock {
    now: u64,
}

impl Clock for ReplayClock {
    fn now_ns(&self) -> u64 {
        self.now
    }
}

fn is_fresh(clock: &impl Clock, received_at: u64, max_age: u64) -> bool {
    let now = clock.now_ns();
    received_at <= now && now - received_at <= max_age
}

fn main() {
    let clock = ReplayClock { now: 1_500 };
    assert!(is_fresh(&clock, 1_450, 100));
    assert!(!is_fresh(&clock, 1_000, 100));
    assert!(!is_fresh(&clock, 1_600, 100));
}
```

决定回放顺序的字段必须来自事件记录本身，不能依赖文件读取程序碰巧先插入哪一条。时间和优先级相同时，使用来源日志中的本地序号；这样即使输入文件行被打乱，事件顺序仍然不变。同一时间和优先级下若出现重复序号，应直接报告录制或合并错误。

```rust,ignore
let mut replay = Replay::default();
replay.schedule(event.at_ns, event.priority, event.local_sequence, event)?;
```

## 23.4 实时运行与历史回放共用核心逻辑

理想结构：

```text
实时消息源 ----\
                -> 内部事件 -> 状态更新 -> 策略与风控 -> 订单意图
历史回放源 ----/                                      |
                                                       v
                                  真实接入层或模拟交易所
```

网络层不必完全共用，但内部事件、订单簿更新、订单状态更新、风控和账务应尽量使用同一套代码。研究与生产各写一套报价逻辑，会很快出现“回测中的规则与实盘不同”的语义漂移。

相同输入、配置和随机种子，必须得到相同的订单意图、模拟成交、仓位和盈亏。随机种子决定伪随机序列从哪里开始，因此它和抽样算法版本也属于实验输入。

## 23.5 模拟交易所，而不是直接改仓位

策略调用 `cancel()` 请求撤单时，模拟订单不能立刻消失。它仍要经历与真实系统相似的步骤：

```text
订单意图 -> 发送延迟 -> 接受或拒绝 -> 进入队列
-> 部分成交、全部成交或收到撤单请求
-> 撤单生效延迟 -> 交易所最终事件 -> 消息返回延迟
```

模拟交易所只产生与真实交易所同类的事件，这些事件仍要经过同一个订单状态更新逻辑和账本。这样才能在线下重现撤单与成交交错、重复消息和未知订单状态。

## 23.6 成交假设从乐观到细致

历史数据通常不能直接告诉你“自己的挂单是否轮到成交”，因此回测必须选择一套成交假设。模型越简单，越要明确它可能偏向哪一边：

| 模型 | 简化规则 | 主要偏差 |
| --- | --- | --- |
| 触价即成交（Touch） | 市场价格碰到挂单价格就成交 | 通常极度乐观 |
| 穿价才成交（Trade-through） | 市场成交价严格穿过挂单价格才成交 | 忽略同价排队 |
| 二档队列模型（L2 queue） | 估计自己前面有多少数量，并随市场事件扣减 | 无法完全区分撤单和成交 |
| 逐订单回放（L3 replay） | 记录并回放每张公开订单的排队变化 | 仍缺本地延迟、隐藏订单等信息 |
| 撮合仿真 | 完整可控事件环境 | 与真实参与者行为有差距 |

至少使用乐观、中性和悲观三组假设。若策略只有在“触价就算成交”时盈利，证据通常不足以进入小范围实盘试运行。

## 23.7 怎样估计自己前面还有多少订单

二档行情只告诉我们每个价格的总数量，不告诉我们每张订单的位置。自己的挂单到达时，需要估计同一价格前面还有多少数量（queue ahead）。之后该档数量减少，还要判断减少来自前方成交还是别处撤单。可以用三种边界：

- 乐观：撤单优先发生在自己前方。
- 悲观：撤单优先发生在自己后方，只有明确成交才减少前方数量。
- 概率：根据历史数据和估计位置，按参数分配减少的数量。

结果必须展示不同排队假设下怎样变化。小额试运行得到的真实成交和成交后价格变化可以用于调整模型，但同一段数据不能既用于调参数，又被当成最终独立验证。

### 配套模拟器的可验证边界

`book/code/src/simulator.rs` 提供三种确定性教学模型：

- `Touch`：对手方最优价格碰到限价就全部成交，是明确的乐观上界。
- `TradeThrough`：只有正确方向的主动成交价严格穿过限价，才判断全部成交。
- `L2Queue`：同价市场成交先消耗前方排队数量，剩余部分才能分给自己的订单；穿价时则成交全部剩余量。

订单先经过发送延迟，真正到达模拟交易所后才能参与后续市场事件。新单确认与成交报告使用不同返回延迟，因此成交消息可以早于接受确认到达订单系统。撤单请求也要等待撤单延迟后才生效；在途中发生的成交仍会报告。模拟器只产生交易所消息，不能直接修改订单系统或账本。

## 23.8 延迟模型

延迟不能只填一个“平均 10 毫秒”。至少要拆分：

- 行情网络传输与本地处理。
- 策略计算与内部队列等待。
- 订单发送与交易所接受。
- 撤单发送与真正生效。
- 成交报告返回与风险状态更新。

延迟参数可以来自真实测量得到的分布。还应把延迟放大到 2 倍、5 倍和 10 倍，观察过期报价成交、成交后价格变化、极端仓位以及策略优势从哪里开始消失。

## 23.9 成本随事件变化

每笔事件计算：

- 挂单与主动成交费率，以及账户当前费率等级。
- 实际发生的资金费现金流。
- 买卖价差、逐档成交和成交价偏差。
- 借贷与利息。
- 资金转移和网络成本。
- 必要时的市场冲击和机会成本。

不要最后统一扣一个平均百分比。策略改变订单类型、频率和持仓路径时，成本也会改变。

## 23.10 市场冲击与容量

非常小的挂单可以暂时忽略自己对中间价的直接影响，但仍不能忽略它在队列中占据的位置。主动成交或规模较大的策略，需要模拟逐档吃单、自己的成交占市场总成交的比例，以及短期和长期市场冲击。

容量不是“把订单乘十再乘 PnL”。规模增长会改变：

- 可成交价格和排队时间。
- 挂单成交与主动成交的比例。
- 对冲成本与完成时间。
- 保证金、费率等级和资金集中在单一交易所的风险。
- 策略对市场状态的反馈。

## 23.11 先把盈亏账对上，再解释收益来源

模拟成交账本、仓位账本和现金账本，应在运行中和每天结束时核对。先验证：

```text
账户权益变化 = 外部转入转出
               + 已实现盈亏 + 未实现盈亏变化
               + 资金费收入 - 交易费用 - 其他成本
```

账务核对通过后，再分析赚取价差、成交后价格变化、持仓重新估值、对冲成交价偏差和剩余未解释部分。回测显示“盈利”，但账本无法闭合，属于实现错误，不是可以忽略的小统计问题。

## 23.12 防止过拟合

- 按时间顺序划分训练、验证和测试数据，最后再保留一段从未使用的数据。
- 向前滚动验证时，每次只用过去数据重新估计。
- 参数搜索要记录全部尝试，不只保存赢家。
- 多重检验降低偶然最好结果的可信度。
- 报告参数邻域，而不是单个最优点。
- 按波动、买卖价差、订单簿深度、趋势和市场环境拆分结果。
- 使用保留时间相关性的重采样方法估计不确定性。

夏普比率不是完整答案。还要看样本覆盖多久、市场规律是否变化、极端亏损、交易频率、最大回撤、策略容量和成本估计误差。

## 23.13 从离线到生产

1. **离线回放**：验证逻辑、偏差和故障事件。
2. **影子运行**：读取生产行情并生成订单意图，但不真正发单，用于检查实时性和稳定性。
3. **测试网**：验证认证、订单状态机、重连和操作流程；不能用测试网成交率推断真实收益。
4. **生产小范围试运行**：只使用单个产品、最小数量和严格限额，比较模拟与真实成交、延迟和费用。
5. **逐步扩大**：每一级都有进入条件、退出条件、负责人和紧急停止方案。

仿真与真实小范围试运行之间的差异，应反馈到模型和风险限制中，不能靠修改实盘报表来隐藏。

## 23.14 研究报告最低结构

- **结论摘要**：结论是什么、证据有多强、是否继续。
- **假设与机制**：收益可能来自谁，为什么可能持续。
- **数据与时点一致**：当时真正可见哪些信息。
- **方法**：成交、延迟和成本怎样模拟。
- **未参与调参的数据结果**与不确定性。
- **盈亏解释、容量和压力情景**。
- **风险、失效条件和无法从数据识别的部分**。
- **影子运行与小范围试运行的校准计划**。

## 23.15 事件调度器的确定性

回放不能只是从头到尾遍历行情文件，因为交易系统自己也会产生带时间的事件：订单到达交易所、撤单生效、资金费结算、定时任务触发和成交报告返回，都可能与市场事件交错发生。

调度器可以按“计划发生时间、事件优先级、本地序号”排序：

```text
10:00:00.000  市场增量消息到达本机
10:00:00.002  策略完成计算
10:00:00.007  新订单到达模拟交易所
10:00:00.009  市场成交消耗同价队列
10:00:00.011  订单接受确认到达订单管理系统
```

![确定性回放事件时间线](assets/replay-timeline.svg)

*图 23-1：订单接受确认可能晚于影响排队的市场事件；模拟器不能按代码调用顺序直接修改订单或仓位。*

回测过拟合、夏普比率统计和时间序列研究资料见[附录 E](appendix-e-references.md)。引用一种统计模型，并不表示回测已经满足时点一致和成交校准要求。

如果订单在第 7 毫秒到达，市场成交在第 9 毫秒发生，它可能参与这次成交；若发送延迟变成 12 毫秒，订单尚未到达，就不可能被第 9 毫秒的市场事件成交。每条行情后都“立即运行策略并假设订单已经生效”，会制造现实中不可能发生的成交。

两个事件时间完全相同时，谁先处理也必须有明确规则。例如先处理交易所市场事件，还是先处理本地定时任务，可能改变恰好处在边界上的成交结果。报告中要说明选择，并测试换一种顺序时结论是否变化。

## 23.16 怎样用少量真实成交调整排队模型

从小范围真实试运行中收集：订单确认时同价位有多少数量、报价已经存在多久、期间市场成交量和档位减少量、真实成交时间与数量，以及成交后的价格变化。然后在相同市场条件下比较模拟与真实结果：

- 给定相同的初始排队估计，成交概率是否接近？
- 首次成交等待时间和完全成交时间是否过快？
- 部分成交数量分布是否合理？
- 是否低估了撤单生效前最后一刻发生的成交？
- 哪些买卖价差、订单簿深度和波动环境下偏差最大？

不要只调整一个参数，让模拟总成交数与真实总成交数相同。模型可能在平静期给出过多成交、在极端期给出过少成交，恰好在总数上互相抵消。调整参数和最终验证必须使用不同时间段，并保留旧模型结果，避免每次出现真实偏差后都靠追着数据改参数来“解释”。

## 23.17 统计显著不等于可交易

一个信号在百万条事件上得到很小的 p 值，说明它不太像纯随机结果，但经济效果可能只有 0.2 个基点，而费用与模型误差却有 5 个基点。反过来，若少量极端时段贡献了大部分盈亏，普通误差估计又可能低估真正风险。

报告需要同时给：

- 效果大小和置信区间。
- 样本数、独立事件近似和时间跨度。
- 交易频率、信号触发频率和可执行容量。
- 参数/特征尝试次数。
- 不同日期、市场环境和交易所中的稳定性。
- 成本、延迟和排队误差下的盈亏边界。

相邻市场事件往往非常相似，随机打散训练和测试数据，会让两边共享几乎相同的市场状态。应按时间块切分，向前滚动验证，并在边界删除会跨区间读取未来结果的样本、留出隔离时间。最后一段数据要等研究决定基本固定后才打开。

## 23.18 模拟与实盘偏差表

每次影子运行或小范围试运行后，都要维护模拟与实际差异，而不是只比较总盈亏：

| 比较维度 | 模拟 | 实际 | 可能原因 | 下一步验证 |
| --- | --- | --- | --- | --- |
| 发送到确认的第 99 百分位延迟 | 18 ms | 41 ms | 网络或网关抖动 | 分地区测量 |
| 挂单成交率 | 12% | 6% | 排队模型过于乐观 | 按订单簿深度校准 |
| 不利的成交后价格变化 | -2 bps | -7 bps | 撤单生效过慢 | 注入真实撤单延迟 |
| 主动成交费率 | 4 bps | 5 bps | 费率等级已过期 | 核对产品规则和账单样本 |
| 极端仓位 | 0.4 | 0.9 | 多笔成交并非独立 | 按市场环境建立成交模型 |

模型升级时要说明修正了哪一项偏差，以及在未参与修改的新数据上是否真正改善。模拟永远不会变成真实交易；目标是让重要偏差可以测量、有明确边界，并反映到风险限制中。

## 23.19 必做实验

1. 使用配套模拟器，让同一订单分别运行触价成交、穿价成交和三组二档排队参数，比较成交与仓位。
2. 将下单和撤单延迟扩大到 2 倍、5 倍和 10 倍。
3. 改变挂单与主动成交费率和对冲频率，判断收益是否依赖手续费返还。
4. 在断线期间禁止交易，并与错误沿用旧订单簿的结果比较。
5. 用一段小范围真实数据调整模型后，在下一段从未使用的数据上验证。

本章完成标准：任何收益曲线都附带时点一致说明、成交/延迟/成本假设、账本对账、敏感性、策略容量，以及不能直接外推到实盘的部分。

## 23.20 回顾与下一章

事件驱动回测重建的是“当时系统能够知道什么、做到什么”，不是让策略读取一张已经包含全部未来的历史表。调度器按明确时间与优先级处理市场消息、定时任务、订单发送、确认、成交和资金费；每次决定只能使用此前已经到达本机的数据。两个事件排序字段完全相同时，必须拒绝输入或用明确规则决定先后，不能悄悄依赖文件行顺序。

实时运行与历史回放应共用订单簿、订单状态、风控和账本更新逻辑，只替换时钟、消息来源、真实或模拟交易所，以及外部动作执行方式。模拟交易所生成消息，不能直接修改策略仓位。结果必须同时给出费用、延迟、成交、市场冲击、容量和账本核对，并通过多组假设展示收益对模型的依赖程度。

下一章会集中处理最敏感的部分：模拟订单何时有资格成交，前方排队数量怎样减少，撤单何时真正生效，以及怎样用新的真实数据调整模型，而不是把一个全局成交概率调到“看起来正确”。
