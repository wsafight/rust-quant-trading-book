# 第五部分导读：证明结果，也准备面对失败

一个回测框架能运行，不代表结果可信；一个服务持续在线，也不代表资金风险受控。研究与生产看似处于开发流程两端，实际共享同一项要求：每个结论都能追到输入、版本、时间和假设，并在偏差出现时采取明确行动。

## 从历史事件到运行证据

| 章节 | 要排除的虚假确定性 | 主要证据 |
| --- | --- | --- |
| 第 23 章 | 历史数据天然可见、订单天然成交 | 当时可见的数据、成本和敏感性 |
| 第 24 章 | 一个成交参数适合所有状态 | 调参与验证分离、条件分布与拒绝标准 |
| 第 25 章 | 显著结果等于可交易收益 | 时间切分、不确定区间和尝试记录 |
| 第 26 章 | 进程存活等于系统安全 | 服务目标、告警、降级、处置手册与演练 |

研究生成模型和参数，生产生成真实延迟、成交与故障观察；二者应该形成校准循环，而不是两套互不相干的代码。

```text
历史/实盘事实 -> 数据版本 -> 仿真与研究 -> 阶段决策
      ^                                      |
      |                                      v
偏差报告 <- 真实 fill/latency/markout <- shadow/受控发布
```

## 带着一个“漂亮结果”阅读

假设研究报告显示某个 imbalance 信号年化 Sharpe 为 3。先暂停参数调优，依次检查：

- feature 在 decision time 是否已经到达本地？
- 相邻样本是否重叠，区间估计是否尊重时间相关？
- maker fill 是否只在信号失败时发生，是否存在选择偏差？
- fee、funding、撤改单、排队和延迟是否进入仿真？
- 参数尝试了多少次，最终 holdout 是否真的未见？
- 结果集中在哪些 venue、时段或极端事件？
- 真实运行以什么指标判断模型应降级或退出？

可信研究的价值不在于消灭不确定性，而在于准确描述不确定性会怎样改变决策。

## 保持同一套领域逻辑

实时运行与历史回放应共享订单簿、订单管理、风险和账本状态更新逻辑，只替换时钟、事件来源、交易所或模拟器，以及动作输出。如果回测直接修改仓位，生产系统却根据成交入账，两条路径验证的根本不是同一套系统。

完全相同也不是目标。模拟器需要明确标记自己无法观测的 queue、隐藏流动性和其他参与者反应；生产路径需要处理认证、资产隔离和人工审批。共享的是领域不变量，不是假装环境没有差别。

## 进入下一部分前

通过检查点五时，你应能从固定 manifest 重放同一结果，展示乐观、基准和悲观成交假设，说明 holdout 与多重尝试，注入一种部分故障，并用账本和远端事实完成恢复审批。

第六部分不再引入大块新知识，而是要求你把前面的证据压缩成可运行项目、书面报告和清晰叙述。它检验的是整合能力与诚实边界。
