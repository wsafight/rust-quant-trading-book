# 附录 J 三条毕业方向

全书提供共同基础，但“量化工程师”并不是单一岗位。完成第五个检查点后，读者应选择一条方向做深，而不是同时扩展更多交易所、产品、模型和基础设施。

三条方向共享以下毕业底线：

- 领域值有单位、身份和版本；
- 状态转换可测试、可回放；
- 超时、乱序、重复和重启有明确动作；
- execution、position、cash 和 PnL 可对账；
- 研究不使用未来信息，成交模型显示假设；
- 项目能由他人独立复现；
- 离线、shadow、testnet、canary 和 production 证据严格区分。

## J.1 怎样选择方向

| 更感兴趣的问题 | 推荐方向 |
| --- | --- |
| 怎样稳定接收事实并在故障后恢复 | 交易系统工程 |
| 一个信号是否真实、稳健且可成交 | 量化研究工程 |
| 怎样完成订单并限制仓位与损失 | 执行与风险工程 |

如果暂时无法选择，先完成共享版第 27 章，再根据最愿意连续深挖十个问题的模块决定。方向不是永久职业标签，而是让毕业项目形成足够深度。

## J.2 方向 A：交易系统工程

### 核心能力

- 公开与私有连接生命周期；
- snapshot/delta 同步和数据新鲜度；
- venue capability 与协议演进；
- OMS、事件日志、快照、幂等和对账；
- 背压、容量、可观测性、发布和恢复。

### 毕业项目

构建一个单交易所、单产品的离线或 shadow 系统。它应记录公开行情，重建订单簿，接收模拟或测试环境的订单事件，维护 OMS 与账本，并演示 gap、timeout、private-stream disconnect 和 restart。

### 必须提供的证据

- 协议与产品规则版本；
- 原始消息和数据质量报告；
- task/owner/channel 图；
- 至少十条订单故障序列；
- 重启前后状态和账务 checksum；
- 目标负载下的队列年龄与尾延迟；
- 处置手册和恢复审批记录。

### 作品集验收表

每项 0～2 分；“协议事实”和“恢复闭环”任一为 0 不通过，建议总分至少 8 分。

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 协议事实 | 依赖猜测或当前网页 | 有 fixture 但版本/来源不全 | raw、规则、版本、契约测试可追溯 |
| 状态正确性 | 依赖理想顺序 | 覆盖部分异常 | gap、乱序、重复、timeout 均确定 |
| 生命周期 | 无界队列或任务无人负责 | 有边界但关闭/过载含糊 | owner、容量、监督和降级均可解释 |
| 恢复闭环 | 重启即开放交易 | 有查询但审批不完整 | 重放、远端查询、对账和审批齐全 |
| 运行证据 | 只有功能演示 | 有指标但缺环境或关联 | 尾延迟、容量、日志、runbook 可复核 |

### 连续追问

1. snapshot 请求期间 delta 缓存满了怎么办？
2. heartbeat 正常但目标频道停止更新怎么办？
3. 发送完成后响应丢失，怎样防止重复订单？
4. event log 写入一半时进程退出怎么办？
5. 回滚版本后远端旧订单由谁处理？

### 能力边界

离线和 shadow 证明状态与恢复设计，不证明真实 venue SLA、真实资金风险或生产值班经验。

## J.3 方向 B：量化研究工程

### 核心能力

- 原始数据、规范事件、特征和标签 lineage；
- point-in-time 数据与时间序列切分；
- 假设、机制、预测周期和成本门槛；
- 实验 manifest、失败日志和多重尝试控制；
- 成交、延迟、容量与市场环境敏感性。

### 毕业项目

选择一个简单、可解释的微观结构假设，从版本化原始数据生成特征和 label，让所有订单意图先经过独立 hard risk，再进入 simulator；所有 venue report 经过 OMS 和 ledger，最终给出 Reject、Revise 或 Shadow 决策。

### 必须提供的证据

- 数据来源、时间范围、schema 和 checksum；
- feature information set 与 label 时间线；
- train/validation/holdout 切分；
- 包含失败实验的 manifest；
- 多成交模型和延迟敏感性；
- effect size、区间、成本、容量和 regime 结果；
- 一项明确的负结果与停止条件。

### 作品集验收表

每项 0～2 分；“时点一致”和“研究诚实性”任一为 0 不通过，建议总分至少 8 分。

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 数据 lineage | 图表无法追溯 | 有数据版本但链路不全 | raw、事件、样本、实验、报告完整关联 |
| 时点一致 | 使用未来信息或随机切分泄漏 | 基本时间切分 | information set、purge、holdout 明确 |
| 成交与成本 | 触价即成交且忽略成本 | 有单一成本模型 | fill/latency/fee/capacity 多情景 |
| 不确定性 | 只报均值或 Sharpe | 有区间但依赖处理不足 | 时间相关、effect size、模型误差分开 |
| 研究诚实性 | 只保留赢家 | 有失败记录但决定含糊 | 全部尝试、负结果、停止条件和阶段决定齐全 |

### 连续追问

1. 谁为什么会支付这项收益？
2. 决策时每个字段真的已经可见吗？
3. 为什么选择这个 block length？
4. family 中一共尝试了多少假设？
5. touch 换成悲观 queue 后为什么仍可信或不再可信？

### 能力边界

离线结果不能证明实盘成交，shadow 不能证明资金风险，单一市场和短时间结果不能自动外推。

## J.4 方向 C：执行与风险工程

### 核心能力

- 订单类型、TIF、价格/数量舍入与执行成本；
- parent/child 订单、未决撤单和 overfill 边界；
- queue、延迟、冲击、markout 与容量；
- worst-case exposure、保证金和压力情景；
- 对冲路径、kill switch 和风险降级。

### 毕业项目

建立一套可解释的执行与风险模拟：给定 parent order、市场状态和产品规则，生成 child order，经过独立硬风控与模拟 venue，最终比较立即、批量和被动三种执行方案。

### 必须提供的证据

- 产品与订单能力表；
- parent/child 守恒和在途容量测试；
- 不同成交、延迟和冲击模型；
- 仓位、保证金和相关性压力表；
- 对冲 Pareto 图；
- venue 断线、cancel timeout 和 kill 失败演练；
- 风险决定无法被策略绕过的说明。

### 作品集验收表

每项 0～2 分；“数量守恒”和“风险独立性”任一为 0 不通过，建议总分至少 8 分。

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 数量守恒 | child 可 overfill parent | 正常路径正确 | partial/pending/uncertain/cancel race 均守恒 |
| 执行成本 | 只比较成交均价 | 有 fee 或 shortfall | benchmark、未成交、depth、impact 与 markout 齐全 |
| 模型敏感性 | 单一 fill/latency | 有少量情景 | 乐观/基准/悲观、尾延迟和容量完整 |
| 风险独立性 | 策略可绕过限制 | 有 risk 模块但状态不全 | worst case、margin、stale 和 kill 独立 |
| 故障处置 | 故障只记录日志 | 有自动降级 | 对冲断线、timeout、kill 失败与恢复审批可演示 |

### 连续追问

1. pending cancel 为什么仍占 parent capacity？
2. 双边订单同时成交时最坏仓位是多少？
3. 高成交率为什么可能意味着更强逆向选择？
4. 对冲 venue 失联时哪些订单必须停止？
5. kill switch 自身失败怎样升级？

### 能力边界

模型比较不证明已经获得真实排队位置、市场冲击或保证金清算经验，参数必须在真实受控观察中持续校准。

## J.5 三条路线的共同评审

最终演示控制在 20 分钟：

1. 2 分钟说明问题、范围和证据等级；
2. 5 分钟运行正常路径；
3. 5 分钟注入方向相关的关键故障；
4. 5 分钟复核一个数字或状态；
5. 3 分钟说明不能证明什么以及下一阶段需要什么证据。

评审者使用[附录 H](appendix-h-review-scripts.md)，并至少提出一个未预先写在演示脚本中的变化。

## J.6 能力缺口表

选择方向前先填写，不要从想使用的技术栈反推项目范围：

| 能力 | 目标岗位要求 | 当前证据 | 证据等级 | 缺口 | 下一项最小行动 | 截止条件 |

| Rust 领域建模 | 示例：可评审公共 API | 示例：V1 类型与测试 | 能解释权衡 | 缺外部调用者验证 | 请同伴尝试绕过构造器 | 无法构造非法状态 |
| 实时行情 |  |  |  |  |  |  |
| OMS/账本 |  |  |  |  |  |  |
| 研究验证 |  |  |  |  |  |  |
| 性能与生产 |  |  |  |  |  |  |
| 方向专项 |  |  |  |  |  |  |

证据等级只使用：`未开始 / 能按说明运行 / 能独立实现 / 能解释权衡 / 已由他人复现`。没有证据时填“未开始”，不能用“了解”“熟悉”替代。

### 从招聘描述反推缺口

1. 把招聘要求拆成可观察动作，例如“优化低延迟系统”拆成定义路径、固定负载、profile、单变量修改和尾延迟复验。
2. 为每项要求指向一个现有产物，找不到就标记缺口。
3. 只选择一个最影响目标岗位的缺口进入下一学习单元。
4. 写下停止条件，避免项目无限扩张。
5. 更新后请评审者验证证据，不由自己提高等级。

## J.7 毕业判定

满足以下条件才标记为毕业：

- 适用的阶段检查点均达到建议分数：编程零基础读者包括 Gate 0，所有读者包括主线检查点一至五；
- 选择的一条方向产物完整；
- 项目正常、边界和故障路径可运行；
- 一项关键结论由他人复核；
- 所有能力声明不超过当前证据；
- 已列出进入真实团队后仍需补齐的经验。

毕业意味着具备申请并承担初级、范围明确工作的基础，不意味着可以独立批准真实资金策略、绕过团队风控或替代生产值班经验。
