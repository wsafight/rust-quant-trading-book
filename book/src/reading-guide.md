# 全书阅读指南：带着一条交易链路学习

这不是一本需要从第一页连续背到最后一页的语言手册，也不是一本收集交易术语的百科。全书围绕同一条问题链展开：市场发生了什么，系统知道了什么，策略想做什么，交易所实际做了什么，账户最终发生了什么变化，以及我们凭什么相信这些结论。

阅读时始终带着一个最小闭环：

```text
原始行情 -> 有效订单簿 -> 决策快照 -> 订单意图 -> 硬风控
   ^                                             |
   |                                             v
回放证据 <- 账本与对账 <- 成交事实 <- 订单管理系统（OMS） <- 交易所
```

前半本书逐步建立这条链上的类型、状态和运行机制，后半本书则用回测、校准、生产运行和项目交付检验它。某章暂时没有写出完整系统并不意味着它是孤立知识；它提供的是闭环中的一个可信部件。

如果 `bid/ask`、订单簿、maker/taker、ack/fill、仓位和 PnL 仍然陌生，请先读[零基础预备课](beginner-primer.md)。它用一笔订单解释这些词，不要求 Rust 或金融背景。

## 选择适合自己的路径

| 你的起点 | 建议入口 | 不要跳过 | 适合的读法 |
| --- | --- | --- | --- |
| 刚开始系统学习 Rust | 第 1 章 | 第 3、4、6 章与检查点一 | 顺序阅读，每段代码都运行并改坏一次 |
| 有 Rust 或后端经验 | 第 1 章自评，然后第 9 章 | 类型单位、取消语义、未知订单状态 | 先做练习，以失败测试定位缺口 |
| 有量化研究经验 | 第 13 章，再回补第 9–12 章 | 当时可见的数据、成交模型、账本对账 | 每个信号都追问“何时可见、怎样成交” |
| 做过交易接入或平台 | 第 18 章 | 固定测试样本、幂等、启动恢复和硬风控 | 用故障序列评审现有经验边界 |
| 准备作品集或面试 | 第 27、28 章 | 五个阶段检查点 | 先列证据缺口，再回到对应章节 |

“跳读”不是只看熟悉的标题。更有效的办法是先尝试章末练习或阶段演示：能产出代码、测试和解释就继续；只能复述名词就回到正文。

## 一章应该怎样读

每章开头的学习导航给出前置、目标、预计投入与产出。建议把一章分成四次动作：

1. **先读场景**：写下本章要避免的错误，以及错误会怎样影响资金或证据。
2. **再跑最小例子**：先确认原样结果，再改一个边界，使测试或编译明确失败。
3. **完成一个变体**：换单位、事件顺序、延迟或输入规模，验证自己掌握的是规则而不是答案。
4. **留下证据**：保存测试、固定输入样本、设计说明或测量报告，并用自己的话解释限制。

每一节都可以用三个问题检查理解：

- **事实是什么**：来自 raw payload、协议事件、账本记录，还是模型估计？
- **谁拥有状态**：哪个组件可以修改，什么事件触发修改，能否确定性重放？
- **失败后怎样收敛**：停止发布、拒绝增险、重试、对账还是人工审批？

如果一段实现无法回答这三个问题，继续增加代码通常只会扩大模糊边界。

## 贯穿案例怎样逐步长成

书中的 BTC 线性永续简化做市案例会多次出现，但每次关注点不同：

| 阶段 | 暂时忽略 | 本阶段必须证明 |
| --- | --- | --- |
| Rust 基础 | 网络、并发和真实交易所 | 单位正确、非法状态受限、错误可测试 |
| 实时系统 | 策略是否盈利 | 序列连续、背压有界、陈旧数据停止发布 |
| 市场与产品 | 完整生产恢复 | 成本、合约现金流、PnL 和账务方向正确 |
| 交易系统 | 统计显著性 | 适配器、订单管理系统、风险和账本能吸收乱序与失败 |
| 研究与生产 | 真实资金部署 | 回测无前视、成交假设可校准、恢复有证据 |
| 贯穿项目 | 夸大的生产声明 | 一条离线、可复现、可审计的完整故事 |

同一个简化在早期可能合理，在后期却会成为缺陷。例如第 2 章用 `i64` 学习控制流，第 6 章以后跨模块 API 就应使用带单位的 newtype；第 13 章用 touch 讨论盘口，第 23、24 章则必须把它明确标为乐观成交上界。

## 如何使用配套代码

正文中的短代码用于隔离概念，`book/code` 用于验证跨模块边界。先运行：

```bash
cargo test --locked --manifest-path book/code/Cargo.toml
cargo run --locked --manifest-path book/code/Cargo.toml --bin demo
```

阅读 demo 时不要只看最终 PnL。沿事件顺序回答：哪条消息改变了订单状态，重复成交为何没有重复入账，sequence gap 后为何不能继续报价，cancel timeout 后哪些暴露仍被计算，对账依据来自哪里。

遇到较长代码时，可按下面的顺序阅读：公开类型与始终要成立的规则、输入事件、纯状态转换函数、产生的待执行动作、访问网络或磁盘的执行器、固定测试样本。这个顺序比从文件第一行顺读到最后一行更接近系统真实结构。

## 书中的符号和约定

- `tick` 是价格最小单位，`lot` 是数量最小单位；权威订单与账务值默认不使用裸 `f64`。
- `event time` 表示外部事件声称发生的时间，`receive time` 表示本机观察到它的时间；二者不能互换。
- `intent` 表示本地希望执行的动作，`ack` 只表示某层确认，`execution` 才是成交事实。
- `valid` 表示已经通过本地不变量，不等于新鲜、可交易或与远端一致。
- `replay` 表示按明确时钟和顺序重放事实，不等于按文件读取速度重新计算。
- 文中的数值多为教学算例。真实 fee、funding、margin 和 API 规则以带访问日期的官方资料与 fixture 为准。

## 什么算真正完成

读完一章不是把页面滚到底。最低完成证据通常包括：一个正常路径、两个边界路径、一个故障路径，以及一段说明当前模型不能证明什么。

完成一个部分后，进入对应阶段检查点。检查点不是附加习题，而是把多章知识合并成一个可演示产物。如果检查点失败，按其中的回补路径返回具体章节；不要依靠继续往后读来掩盖基础缺口。

最后，把所有产物串成一条可以在十几分钟内解释的证据链。目标不是声称“做过一个量化系统”，而是让读者或面试官能够复现你的输入、观察状态转换、注入失败并验证最终账本。
